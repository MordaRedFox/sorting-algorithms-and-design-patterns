                                  ТУТОРИАЛ
                   Справочник по паттернам проектирования


Паттерны проектирования — это типовые, проверенные решения для часто
возникающих проблем в проектировании ПО. Это не готовый код, а концептуальные
шаблоны или инструкции, как лучше структурировать компоненты системы

              Паттерн "Абстрактная Фабрика" (Abstract Factory)
1) Суть паттерна парой слов:
Паттерн предоставляет интерфейс для создания семейств взаимосвязанных или
взаимозависимых объектов, без указания их конкретных классов. У паттерна есть
абстрактный интерфейс, в котором объявляются методы для создания семейства
объектов (например, колеса и двигатель для машины), а так же абстрактные
интерфейсы этих объектов (колеса и двигатель). Далее уже конкретные фабрики
(например, машина тойота, машина бмв) создают свои конкретные семества объектов
(например, колеса для бмв, двигатель для бмв), но с фабриками и объектами
клиент работает только через абстрактные интерфейсы

2) Проблема, которую решает паттерн:
Представьте, что мы разрабатываем кроссплатформенный UI-фреймворк
(для Windows, macOS, Linux). Нам нужны: Кнопки (Button), Текстовые поля
(TextField), Чекбоксы (Checkbox) и т.д.

Но для каждой ОС эти элементы выглядят и работают по-разному:
• Windows: WinButton, WinTextField, WinCheckbox
• macOS: MacButton, MacTextField, MacCheckbox
• Linux: LinuxButton, LinuxTextField, LinuxCheckbox

Проблема: Как создавать согласованные наборы компонентов для конкретной ОС,
при этом не привязывая клиентский код к конкретным классам?
Без паттерна код превращается в хаос условных операторов:
if (OS == "Windows") {
    button = new WinButton();
    textField = new WinTextField();
} else if (OS == "Mac") {
    button = new MacButton();
    textField = new MacTextField();
}
// ...

3) Структура паттерна Абстрактная Фабрика:

                        ┌───────────────────────────────┐
                        │       AbstractFactory         │
                        ├───────────────────────────────┤
                        │ +createButton(): Button       │
                        │ +createTextField(): TextField │
                        └───────────────────────────────┘
                                        ▲
               ┌────────────────────────┼────────────────────────┐
    ┌──────────┴──────────┐  ┌──────────┴──────────┐  ┌──────────┴──────────┐
    │     WinFactory      │  │      MacFactory     │  │     LinuxFactory    │
    ├─────────────────────┤  ├─────────────────────┤  ├─────────────────────┤
    │ +createButton()     │  │ +createButton()     │  │ +createButton()     │
    │ +createTextField()  │  │ +createTextField()  │  │ +createTextField()  │
    └─────────────────────┘  └─────────────────────┘  └─────────────────────┘

          ┌─────────────────┐                     ┌─────────────────┐
          │    Abstract     │                     │    Abstract     │
          │     Button      │                     │    TextField    │
          ├─────────────────┤                     ├─────────────────┤
          │ +click()        │                     │ +inputText()    │
          └─────────────────┘                     └─────────────────┘
                   ▲                                       ▲
           ┌───────┴───────┐                       ┌───────┴───────┐
┌──────────┴──────┐ ┌──────┴──────────┐ ┌──────────┴──────┐ ┌──────┴──────────┐
│    WinButton    │ │    MacButton    │ │  WinTextField   │ │  MacTextField   │
├─────────────────┤ ├─────────────────┤ ├─────────────────┤ ├─────────────────┤
│ +click()        │ │ +click()        │ │ +inputText()    │ │ +inputText()    │
└─────────────────┘ └─────────────────┘ └─────────────────┘ └─────────────────┘

Ключевые компоненты:
• AbstractFactory — интерфейс с методами создания всех абстрактных продуктов
• ConcreteFactory — конкретные фабрики, реализующие методы создания продуктов
для конкретного семейства (WinFactory, MacFactory, LinuxFactory)
• AbstractProductA, AbstractProductB — абстрактные интерфейсы для продуктов
(Abstract Button, Abstract TextField)
• ConcreteProductA1, ConcreteProductA2, ConcreteProductB1, ConcreteProductB2 —
конкретные реализации продуктов (WinButton, MacButton, WinTextField,
MacTextField)
• Client — использует только интерфейсы AbstractFactory и AbstractProduct

4) Ключевые преимущества паттерна:
• Гарантирует согласованность — все созданные объекты принадлежат
одному семейству
• Изоляция конкретных классов — клиентский код работает только с
абстрактными интерфейсами
• Легкость замены семейств — для смены ОС достаточно заменить одну фабрику
• Принцип единой ответственности — код создания продуктов вынесен в одно место
• Принцип открытости/закрытости — легко добавить новое семейство продуктов без
изменения существующего кода

5) Когда применять паттерн?
✓ Когда система должна быть независима от процесса создания объектов
✓ Когда нужно создавать семейства связанных объектов
✓ Когда требуется предоставить библиотеку продуктов, раскрывая только их
интерфейсы, а не реализации
✓ Когда важно обеспечить совместимость создаваемых объектов

6) Важные замечания!
⨯ Сложность добавления нового продукта — чтобы добавить новый тип продукта
(например, Checkbox), нужно изменить все фабрики и абстрактную фабрику. Это
главный недостаток
⨯ Легкость добавления нового семейства — чтобы добавить новое семейство
(например, LinuxFactory), нужно создать новый набор конкретных продуктов и
новую фабрику


                        Паттерн "Строитель" (Builder)
1) Суть паттерна парой слов:
Паттерн позволяет создавать сложные объекты пошагово, отделяя процесс
конструирования от представления объекта, чтобы один и тот же процесс
конструирования мог создавать разные реализации. У паттерна есть абстракный
интерфейс строителя, которому делегировано создание сложного объекта. Этот
интерфейс используют конкретные строители для создания конкретной реализации
сложного объекта. Процессом создания опционально может управлять "директор"

2) Проблема, которую решает паттерн:
Проблема 1 — Громоздкие конструкторы (Telescoping Constructor):
// Анти-паттерн: конструктор со множеством параметров
House* house = new House(4, 2, true, true, false, true, "кирпич", "шифер");
// Что означают эти параметры? Какой из них отвечает за наличие гаража?

Проблема 2 — Частичная инициализация:
House* house = new House();
house->setWalls(4);
house->setDoors(2);
// А что если забыть вызвать setRoof()?
// Объект в некорректном состоянии!

Проблема 3 — Создание объектов с разными конфигурациями:
Как создать:
• Простой дом (стены + крыша)
• Дом с гаражом
• Дом с бассейном и садом
• Полный "люкс" дом
Без паттерна получается множество перегруженных конструкторов или сложная
логика инициализации

3) Структура паттерна Строитель:

Ключевые компоненты:
• Director (Директор) — управляет процессом строительства, вызывает методы
строителя в определённом порядке. Знает "рецепт" построения объекта
• Builder Interface (Интерфейс строителя) — определяет общие методы для
построения всех частей сложного объекта, а также метод getResult() для
получения готового продукта
• ConcreteBuilder (Конкретные строители) — реализуют интерфейс Builder,
содержат экземпляр продукта, определяют логику построения конкретных
частей продукта
• Product (Продукт) — сложный объект, который строится пошагово. В данном
случае — дом с различными параметрами

4) Ключевые преимущества паттерна:
• Пошаговое создание — можно контролировать процесс конструирования
• Изоляция сложной логики — код создания скрыт в строителе
• Разные представления — один процесс строительства → разные продукты
• Гибкость конфигурации — легко создавать объекты с разным набором свойств
• Улучшенная читаемость — именованные методы вместо множества параметров

5) Когда применять паттерн?
✓ Сложные объекты с множеством параметров (> 4-5 параметров)
✓ Объекты с разными конфигурациями или опциональными полями
✓ Неизменяемые (immutable) объекты
✓ Пошаговая инициализация с валидацией на каждом шаге
✓ Создание различных представлений одного объекта

6) Важные замечания!
⨯ Избыточность кода — нужно писать много boilerplate-кода (повторяющийся код)
⨯ Сложность — дополнительные классы/методы
⨯ Не для простых объектов — overhead не оправдан для простых DTO


                 Паттерн "Фабричный метод" (Factory Method)
1) Суть паттерна парой слов:
Фабричный метод — это порождающий паттерн, который определяет интерфейс для
создания объектов в суперклассе, но позволяет подклассам изменять тип
создаваемых объектов. По сути, это способ делегирования логики создания
объектов дочерним классам, не привязывая основной код к конкретным
классам продуктов

2) Проблема, которую решает паттерн:
Представьте, что мы разрабатываем систему логистики, которая должна работать
с разными видами транспорта:

Проблема 1 — Жёсткая привязка к конкретным классам:
Transport* transport;
if (type == "truck") {
    transport = new Truck();
} else if (type == "ship") {
    transport = new Ship();
} else if (type == "plane") {
    transport = new Plane();
}
// Что делать, если нужно добавить новый вид транспорта?

Проблема 2 — Нарушение принципа открытости/закрытости:
Каждый раз при добавлении нового типа продукта приходится модифицировать
существующий код, добавляя новые условия

Проблема 3 — Дублирование кода:
Если в разных частях программы требуется создавать одни и те же объекты,
логика создания дублируется

3) Структура паттерна Фабричный метод:

          ┌─────────────────────────────────────────────────────────┐
          │                        Creator                          │
          ├─────────────────────────────────────────────────────────┤
          │ + someOperation(): void                                 │
          │ # factoryMethod(): Product                              │
          ├─────────────────────────────────────────────────────────┤
          │ someOperation() {                                       │
          │   Product product = factoryMethod();                    │
          │   product.use();                                        │
          │ }                                                       │
          └────────────────────────────┬────────────────────────────┘
                                       │
                                       │
                         ┌─────────────┴─────────────┐
                         │                           │
                         ▼                           ▼
                ┌──────────────────┐       ┌──────────────────┐
                │ ConcreteCreator1 |       │ ConcreteCreator2 |
                ├──────────────────┤       ├──────────────────┤
                │- field1          │       │- field2          │
                ├──────────────────┤       ├──────────────────┤
                │+ factoryMethod() |       │+ factoryMethod() |
                └────────┬─────────┘       └─────────┬────────┘
                         │                           │
                         │                           │ 
                         ▼                           ▼
                ┌──────────────────┐       ┌──────────────────┐
                │ ConcreteProduct1 |       │ ConcreteProduct2 |
                ├──────────────────┤       ├──────────────────┤
                │+ use()           │       │+ use()           │
                └──────────────────┘       └──────────────────┘
                         ▲                           ▲
                         └─────────────┬─────────────┘
                                       │
                             ┌─────────┴─────────┐
                             │     Product       │
                             ├───────────────────┤
                             │+ use()            │
                             └───────────────────┘

Ключевые компоненты:
• Создатель (Creator) — объявляет фабричный метод factoryMethod(), который
возвращает объект типа Product. Создатель может содержать базовую бизнес-логику,
которая зависит от объектов-продуктов, возвращаемых фабричным методом
• Конкретные создатели (ConcreteCreators) — переопределяют фабричный метод,
чтобы возвращать экземпляры конкретных продуктов. Каждый конкретный создатель
отвечает за создание определённого типа продукта
• Продукт (Product) — определяет интерфейс объектов, создаваемых фабричным
методом
• Конкретные продукты (Concrete Products) — различные реализации интерфейса
Product

4) Ключевые преимущества паттерна:
• Устранение жёсткой привязки — основной код работает с абстракциями, а не с
конкретными классами
• Принцип единой ответственности — логика создания объектов вынесена в
отдельные классы
• Принцип открытости/закрытости — легко добавлять новые типы продуктов, не
изменяя существующий код
• Упрощение поддержки — локализация кода создания объектов
• Гибкость подклассов — подклассы могут изменять тип создаваемых объектов

5) Когда применять паттерн?
✓ Когда заранее неизвестны типы объектов — система должна работать с объектами,
конкретные классы которых определяются во время выполнения
✓ Когда класс делегирует ответственность создания объектов своим подклассам
✓ Когда нужно предоставить возможность расширения — библиотека или фреймворк
должны позволять расширять свои внутренние компоненты
✓ Когда необходимо локализовать логику создания объектов — чтобы избежать
дублирования кода в разных частях программы
✓ Когда нужно обеспечить гибкость и расширяемость системы

6) Важные замечания!
⨯ Усложнение кода — необходимо создавать много дополнительных классов
⨯ Может привести к разрастанию иерархии — для каждого нового продукта нужен
новый создатель


                       Паттерн "Прототип" (Prototype)
1) Суть паттерна парой слов:
Паттерн Прототип позволяет создавать новые объекты путем копирования
существующих объектов-прототипов, вместо создания объектов через конструктор.
Объект-прототип служит образцом для создания новых объектов, что позволяет
избежать сложной инициализации и повысить производительность в случаях, когда
создание объекта с нуля затратно. То есть конкретные прототипы создают объект
по умолчанию, который можно затем модифицировать с помощью сеттеров

2) Проблема, которую решает паттерн:
Проблема 1 — Сложное и дорогое создание объектов:
// Объект требует длительной инициализации (загрузка данных, вычисления)
DatabaseConnection* conn = new DatabaseConnection();
conn->loadConfiguration("config.xml");
conn->establishConnection(); // Долгая операция
conn->authenticate();
// Что если нужно ещё одно такое же подключение?

Проблема 2 — Много параметров и сложная конфигурация:
Car* car = new Car("V8", "красный", "кожа", true, true, false, "спорт", 19);
// Создание аналогичного автомобиля требует повторной передачи всех параметров

Проблема 3 — Скрытые зависимости и приватное состояние:
Объект может иметь внутреннее состояние, недоступное для внешнего кода, но
необходимое для его работы. Как создать точную копию?
Без паттерна пришлось бы:
• Повторять сложную логику инициализации
• Раскрывать внутреннее состояние объекта
• Использовать громоздкие конструкторы копирования

3) Структура паттерна Прототип:

                    ┌─────────────────────────────┐
                    │          Prototype          │
                    │    (интерфейс прототипа)    │
                    ├─────────────────────────────┤
                    │ + clone(): Prototype*       │
                    └─────────────────────────────┘
                                   ▲
                                   │
                   ┌───────────────┴────────────────┐
         ┌─────────┴────────┐              ┌────────┴─────────┐
         │ ConcretePrototype│              │ ConcretePrototype│
         │        A         │              │        B         │
         ├──────────────────┤              ├──────────────────┤
         │ - field1         │              │ - field2         │
         │ - field2         │              │ - field3         │
         ├──────────────────┤              ├──────────────────┤
         │ + clone()        │              │ + clone()        │
         │ + operation()    │              │ + operation()    │
         └──────────────────┘              └──────────────────┘

Ключевые компоненты:
• Prototype (Прототип) — объявляет интерфейс для клонирования самого себя
• ConcretePrototype (Конкретный прототип) — реализует операцию клонирования,
создавая точную копию себя
• Client (Клиент) — создает новый объект, обращаясь к прототипу с запросом
клонировать себя

4) Ключевые преимущества паттерна:
• Упрощение создания сложных объектов — не нужно повторять логику инициализации
• Повышение производительности — клонирование обычно быстрее создания с нуля
• Сокрытие сложности создания — клиент не знает, как устроен объект
• Гибкость конфигурации — можно создавать объекты с разным состоянием на
основе прототипов
• Работа со сложными графами объектов — глубокое копирование сложных структур
• Альтернатива наследованию — вместо создания иерархий классов можно
использовать клонирование

5) Когда применять паттерн?
✓ Когда создание объекта требует больших ресурсов (база данных, сетевые запросы)
✓ Когда система не должна зависеть от того, как создаются и компонуются объекты
✓ Когда нужно создавать объекты с определенным начальным состоянием
✓ Когда объект имеет множество возможных конфигураций
✓ Когда требуется избежать построения иерархий фабрик или классов-создателей
✓ При работе с объектами, имеющими сложную структуру (например, составные
объекты)

6) Важные замечания!
⨯ Сложность реализации глубокого копирования — нужно корректно копировать все
ссылки и внутренние объекты
⨯ Опасность циклических ссылок — при клонировании сложных графов объектов
⨯ Нарушение инкапсуляции — если для клонирования требуется доступ к приватным
полям
⨯ Не всегда ясно, какой тип объекта будет создан — клиент работает с
интерфейсом Prototype


                       Паттерн "Одиночка" (Singleton)
1) Суть паттерна парой слов:
Одиночка — это порождающий паттерн проектирования, который гарантирует, что у
класса есть только один экземпляр, и предоставляет глобальную точку доступа к
этому экземпляру. Паттерн контролирует создание объекта, скрывая конструктор и
предоставляя статический метод для получения единственного экземпляра класса

2) Проблема, которую решает паттерн:
Проблема 1 — Множественные экземпляры глобальных ресурсов:
// Плохо: разные части программы создают свои экземпляры
Logger* logger1 = new Logger();
Logger* logger2 = new Logger();
// Теперь у нас два разных логгера с разным состоянием!

Проблема 2 — Конкурентный доступ к общему ресурсу:
• Конфигурация приложения
• Кэш данных
• Подключение к базе данных
• Логгер
• Менеджер очереди задач

Проблема 3 — Неконтролируемое создание объектов:
Без паттерна любой код может создать новый экземпляр, что приводит к
расходованию лишней памяти, несогласованному состоянию, конфликтам при работе
с общими ресурсами

3) Структура паттерна Одиночка:

            ┌─────────────────────────────────────┐
            │              Singleton              │
            ├─────────────────────────────────────┤
            │ - static instance: Singleton*       │  // Одноразовая инициализация
            │ - data: string                      │
            ├─────────────────────────────────────┤
            │ - Singleton()                       │  // Приватный конструктор
            │ - Singleton(const Singleton&)       │  // Запрет копирования
            │ - operator=(const Singleton&)       │  // Запрет присваивания
            │                                     │
            │ + static getInstance(): Singleton*  │
            │ + someBusinessLogic(): void         │
            └─────────────────────────────────────┘

Ключевые компоненты:
Singleton (Одиночка) — класс, который:
• Содержит приватное статическое поле instance для хранения единственного
экземпляра
• Имеет приватный конструктор (запрещает создание через new)
• Предоставляет публичный статический метод getInstance() для доступа к
экземпляру
• Обычно содержит бизнес-логику

4) Ключевые преимущества паттерна:
• Гарантирует единственный экземпляр — полный контроль над созданием объекта
• Глобальная точка доступа — удобный способ получения экземпляра из любой
части программы
• Ленивая инициализация — объект создаётся только при первом вызове
getInstance()
• Контроль над ресурсами — управление доступом к общим ресурсам (БД,
файлы, сеть)
• Экономия памяти — избегание дублирования объектов

5) Когда применять паттерн?
✓ Управление общими ресурсами — подключение к базе данных, файловые системы
✓ Конфигурация приложения — глобальные настройки, которые должны быть
согласованными
✓ Кэширование данных — централизованное хранилище кэша
✓ Логирование — единый логгер для всего приложения
✓ Менеджеры — менеджер очереди задач, пул потоков, диспетчер памяти
✓ Когда требуется контроль над созданием экземпляров — например, для
ограничения количества подключений

6) Важные замечания!
⨯ Нарушение принципа единой ответственности — класс решает две задачи:
бизнес-логику и контроль создания
⨯ Проблемы с тестированием — сложно тестировать из-за глобального состояния
⨯ Проблемы с многопоточностью — требует дополнительной синхронизации
⨯ Скрытые зависимости — код зависит от глобального состояния, что усложняет
понимание кода
⨯ Сложность с жизненным циклом — порядок инициализации и разрушения в сложных
системах

                       Паттерн "Адаптер" (Adapter)
1) Суть паттерна парой слов:
Адаптер — это структурный паттерн проектирования, который позволяет объектам
с несовместимыми интерфейсами работать вместе. Он выступает в роли
"переводчика" или "прослойки" между двумя объектами, преобразуя интерфейс
одного класса в интерфейс, ожидаемый другим классом. Паттерн оборачивает
один из объектов, скрывая от клиента сложность преобразования

2) Проблема, которую решает паттерн:
Представьте, что у нас есть современное приложение для обработки платежей,
которое работает с объектами типа ModernPaymentProcessor с методом
processPayment(amount). Но нам нужно интегрировать старую библиотеку для
платежей LegacyPaymentSystem, у которой есть метод makePayment(sum) с
другим названием и другим форматом параметров

Проблема 1 — Несовместимые интерфейсы:
// Современный код ожидает такой интерфейс:
ModernPaymentProcessor* processor = getModernProcessor();
processor->processPayment(100.50);  // принимает double
// Но у нас есть только старая система:
LegacyPaymentSystem* legacy = getLegacySystem();
legacy->makePayment("100.50");  // принимает string!

Проблема 2 — Невозможность изменить исходный код:
• Старая система закрыта для модификаций (библиотека от третьей стороны)
• Современная система тоже не должна меняться
• Нужно "подружить" две системы без изменения их кода

Проблема 3 — Множественные адаптации:
Что если нужно работать с несколькими старыми системами одновременно?
Или добавить поддержку новых платежных систем с разными API?
Без паттерна пришлось бы:
• Изменять клиентский код для работы с каждой системой отдельно
• Создавать условные конструкции для обработки разных типов
• Дублировать код преобразования данных в разных местах программы

3) Структура паттерна Адаптер:

ВЕРСИЯ 1: Адаптер через наследование (Adapter через Class)

       ┌─────────────────────┐                     ┌─────────────────────┐
       │       Client        │                     │       Target        │
       │      (Клиент)       │                     │ (Целевой интерфейс) │
       ├─────────────────────┤                     ├─────────────────────┤
       │                     │                     │ + request(): void   │
       └─────────────────────┘                     └──────────┬──────────┘
                                                              │
                                                              │
                                                              │ использует
                                                              |
  ┌───────────────────────────────┐                           |
  │            Adapter            │                           ▼
  │           (Адаптер)           |             ┌───────────────────────────┐
  ├───────────────────────────────┤             │          Adaptee          │
  │ + request(): void             │◄────────────┤   (Адаптируемый  класс)   │
  │                               │  наследует  ├───────────────────────────┤
  │ request() {                   │             │ + specificRequest(): void │
  │   adaptee->specificRequest(); │             └───────────────────────────┘
  │ }                             │
  └───────────────────────────────┘

ВЕРСИЯ 2: Адаптер через композицию (Object Adapter) - БОЛЕЕ ГИБКИЙ

       ┌─────────────────────┐                  ┌─────────────────────┐
       │       Client        │                  │      Target         │
       │      (Клиент)       │                  │ (Целевой интерфейс) │
       ├─────────────────────┤                  ├─────────────────────┤
       │                     │                  │ + request(): void   │
       └─────────────────────┘                  └──────────┬──────────┘
                                                           │
                                                           │
                                                           │ использует
                                                           |
  ┌───────────────────────────────┐                        |
  │            Adapter            │                        ▼
  │           (Адаптер)           │          ┌───────────────────────────┐
  ├───────────────────────────────┤          │          Adaptee          │
  │ - adaptee: Adaptee*           │─────────►│   (Адаптируемый класс)    │
  ├───────────────────────────────┤ содержит ├───────────────────────────┤
  │ + request(): void             │          │ + specificRequest(): void │
  │                               │          └───────────────────────────┘
  │ request() {                   │
  │   adaptee->specificRequest(); │
  │   // возможна дополнительная  |
  |   // логика преобразования    |
  │ }                             │
  └───────────────────────────────┘

Ключевые компоненты:
• Target (Целевой интерфейс) — интерфейс, который ожидает клиент. В нашем
примере: ModernPaymentProcessor с методом processPayment()
• Client (Клиент) — класс, который работает с объектами через целевой интерфейс
• Adaptee (Адаптируемый класс) — существующий класс с несовместимым интерфейсом,
который нужно адаптировать. В нашем примере: LegacyPaymentSystem с методом
makePayment()
• Adapter (Адаптер) — класс, который реализует целевой интерфейс и "переводит"
запросы клиента в формат, понятный адаптируемому классу

4) Ключевые преимущества паттерна:
• Совместимость несовместимого — позволяет работать вместе классам с разными
интерфейсами
• Принцип единой ответственности — логика преобразования вынесена в отдельный
класс
• Принцип открытости/закрытости — можно вводить новые адаптеры без изменения
существующего кода клиента
• Переиспользование существующих классов — можно использовать старый код в
новых системах
• Гибкость — можно адаптировать сразу несколько классов через один адаптер
• Прозрачность для клиента — клиент не знает, что работает с адаптером, а не с
реальным объектом

5) Когда применять паттерн?
✓ Интеграция старого кода с новым — когда нужно использовать унаследованные
классы в современной системе
✓ Работа со сторонними библиотеками — когда API библиотеки не соответствует
ожиданиям вашей системы
✓ Унификация интерфейсов — когда несколько классов выполняют схожую функцию,
но имеют разные интерфейсы
✓ Постепенная миграция — при поэтапном переходе со старой системы на новую
✓ Тестирование — создание заглушек (mocks/stubs) для тестирования
✓ Многоплатформенная разработка — адаптация системных API под единый интерфейс

6) Важные замечания!
⨯ Усложнение кода — вводится дополнительный слой абстракции
⨯ Необходимость создания множества адаптеров — если нужно адаптировать много
разных классов
⨯ Ограничения наследования — в версии Class Adapter нельзя адаптировать
несколько классов одновременно (проблема множественного наследования в языках
типа Java, C#)
⨯ Производительность — небольшой overhead из-за дополнительного вызова методов
⨯ Маскировка проблем — может скрыть плохой дизайн адаптируемого класса


                           Паттерн "Мост" (Bridge)
1) Суть паттерна парой слов:
Мост — это структурный паттерн проектирования, который разделяет абстракцию и
ее реализацию, позволяя изменять их независимо друг от друга. Паттерн
предлагает заменить наследование композицией: вместо создания множества
подклассов, зависящих от конкретной реализации, мы выделяем общую абстракцию
и выносим реализацию в отдельную иерархию классов. Это позволяет менять или
расширять реализацию без изменения клиентского кода

2) Проблема, которую решает паттерн:
Проблема 1 — Разрастание иерархии классов (классовый взрыв):
Предположим, у нас есть иерархия устройств: Устройство → Телевизор, Радио,
Компьютер. Также есть несколько пультов управления: БазовыйПульт, ПультСГолосом,
ПультСМоторами. Если создавать подклассы для каждой комбинации (например,
ТелевизорСБазовымПультом, ТелевизорСПультомСГолосом, РадиоСБазовымПультом и
т.д.), то количество классов растёт экспоненциально
При добавлении нового типа устройства или нового пульта количество классов
увеличивается ещё больше

Проблема 2 — Жесткая связь абстракции и реализации:
В традиционном наследовании изменение в реализации (например, добавление новой
функции в пульт) требует изменения всех подклассов устройств, которые
используют этот пульт. Это нарушает принцип открытости/закрытости

Проблема 3 — Сложность поддержки и тестирования:
Большое количество классов делает код громоздким, сложным для понимания и
тестирования. Изменение одной детали реализации может привести к необходимости
изменять множество классов

3) Структура паттерна Мост:

                ┌─────────────────────────────────────────┐
                │               Abstraction               │
                │              (Абстракция)               │
                ├─────────────────────────────────────────┤
                │ - implementor: Implementor              │
                ├─────────────────────────────────────────┤
                │ + operation(): void                     │
                │   // делегирует работу implementor      │
                └────────────────────┬────────────────────┘
                                     │
                                     │ содержит ссылку на
                                     ▼
                ┌─────────────────────────────────────────┐
                │               Implementor               │
                │               (Реализация)              │
                ├─────────────────────────────────────────┤
                │ + operationImpl(): void                 │
                └─────────────────────────────────────────┘
                                     ▲
                                     │
                      ┌──────────────┴──────────────┐
      ┌───────────────┴────────┐           ┌────────┴───────────────┐
      │  ConcreteImplementorA  │           │  ConcreteImplementorB  │
      ├────────────────────────┤           ├────────────────────────┤
      │ + operationImpl()      │           │ + operationImpl()      │
      └────────────────────────┘           └────────────────────────┘

Ключевые компоненты:
• Abstraction (Абстракция) — определяет интерфейс абстракции и содержит ссылку
на объект Implementor. Делегирует выполнение операций этому объекту
• Implementor (Реализатор) — определяет интерфейс для классов реализации. Этот
интерфейс не обязательно должен точно соответствовать интерфейсу Abstraction
• ConcreteImplementor (Конкретный реализатор) — содержит конкретную реализацию
интерфейса Implementor
• Client (Клиент) — работает только с объектами Abstraction, не заботясь о
деталях реализации. Клиент связывает абстракцию с конкретной реализацией через
конструктор или сеттер

4) Ключевые преимущества паттерна:
• Разделение абстракции и реализации — можно изменять их независимо
• Устранение взрыва подклассов — вместо экспоненциального роста классов
используется композиция
• Принцип открытости/закрытости — легко добавлять новые абстракции и реализации
без изменения существующего кода
• Улучшенная поддерживаемость — код становится чище, логика разделена
• Гибкость во время выполнения — можно динамически менять реализацию у
абстракции

5) Когда применять паттерн?
✓ Когда нужно разделить монолитный класс, который объединяет несколько
независимых измерений изменчивости
✓ Когда нужно расширять класс в двух независимых плоскостях (абстракция и
реализация)
✓ Когда нужно переключать реализации во время выполнения
✓ Когда нужно избежать постоянного создания подклассов из-за комбинаций
абстракций и реализаций
✓ Когда нужно скрыть детали реализации от клиентского кода

6) Важные замечания!
⨯ Усложнение структуры — вводит дополнительный уровень абстракции, что может
быть избыточно для простых случаев
⨯ Требует тщательного проектирования — необходимо правильно выделить
абстракцию и реализацию, что не всегда тривиально
⨯ Может затруднить чтение кода — если иерархии становятся глубокими, сложнее
отследить поток выполнения
⨯ Не всегда очевидна необходимость — в простых системах проще использовать
наследование


                      Паттерн "Компоновщик" (Composite)
1) Суть паттерна парой слов:
Компоновщик — это структурный паттерн проектирования, который позволяет
сгруппировать множество объектов в древовидную структуру и работать с ней так,
как будто это единый объект. Паттерн позволяет клиенту одинаково обращаться
как к отдельным объектам, так и к их группам (композициям), не делая между ними
различий

2) Проблема, которую решает паттерн:
Проблема 1 — Обработка древовидных структур объектов:
Предположим, у нас есть файловая система: есть файлы и папки, которые могут
содержать файлы и другие папки. Нужно реализовать операцию «вычислить общий
размер» как для отдельного файла, так и для папки со всем её содержимым

Проблема 2 — Различия в обработке одиночных и составных объектов:
Без паттерна клиенту приходится проверять тип объекта и обрабатывать его
по-разному:
if (isFile(item)) {
    totalSize += item->getSize();
} else if (isFolder(item)) {
    for (auto child : item->getChildren()) {
        totalSize += child->getSize(); // Рекурсивный обход
    }
}

Проблема 3 — Сложность добавления новых операций:
Каждая новая операция (например, «поиск файла», «удаление») требует изменения
кода как для файлов, так и для папок

3) Структура паттерна Компоновщик:

                      ┌───────────────────────────────────┐
                      │             Component             │
                      │      (Абстрактный компонент)      │
                      ├───────────────────────────────────┤
                      │ + operation(): void               │
                      │ + add(Component): void            │
                      │ + remove(Component): void         │
                      │ + getChild(int): Component        │
                      └─────────────────┬─────────────────┘
                                        │
                 ┌──────────────────────┴─────────────────────┐
                 │                                            │
                 ▼                                            ▼
     ┌───────────────────────┐                     ┌───────────────────────┐
     │         Leaf          │                     │       Composite       │
     │ (Листовой компонент)  │                     │ (Составной компонент) │
     ├───────────────────────┤                     ├───────────────────────┤
     │ + operation()         │                     │ - children:           │
     └───────────────────────┘                     │   List<Component>     │
                                                   ├───────────────────────┤
                                                   │ + operation()         │
                                                   │ + add(Component)      │
                                                   │ + remove(Component)   │
                                                   │ + getChild(int)       │
                                                   └───────────────────────┘

Ключевые компоненты:
• Component — общий интерфейс для всех элементов дерева. Определяет методы для
работы как с простыми, так и со сложными элементами
• Leaf — листовой элемент, не имеющий дочерних элементов. Реализует операции,
применимые к самому себе
• Composite — составной элемент, который может содержать другие компоненты
(листья или другие композиты). Делегирует выполнение операций своим дочерним
элементам, часто рекурсивно
• Client — работает с компонентами через общий интерфейс Component

4) Ключевые преимущества паттерна:
• Единообразная работа — клиент не различает отдельные объекты и их композиции
• Упрощение кода клиента — не требуется проверять тип объекта и выполнять
разные действия
• Лёгкость добавления новых видов компонентов — можно добавлять новые типы
листьев и композитов, не изменяя существующий код
• Упрощение архитектуры — вместо множества условных операторов используется
полиморфизм и рекурсия
• Поддержка рекурсивных структур — идеально подходит для работы с деревьями

5) Когда применять паттерн?
✓ Когда нужно представить древовидную структуру объектов
✓ Когда клиент должен единообразно работать как с отдельными объектами, так и
с их группами
✓ Когда необходимо выполнять операции над всей иерархией объектов рекурсивно
✓ Когда требуется упростить код, убрать множество проверок типов и условных
операторов

6) Важные замечания!
⨯ Может нарушить принцип единой ответственности — интерфейс Component может
содержать методы, неприменимые для Leaf (например, add() для файла)
⨯ Сложность контроля типов — клиент может попытаться добавить лист в другой
лист, что логически некорректно
⨯ Проблемы с производительностью — рекурсивные операции над глубокими деревьями
могут быть затратными
⨯ Ограниченная безопасность — в некоторых реализациях приходится жертвовать
безопасностью типов ради единообразия интерфейса
⨯ Не для всех иерархий — если структура не является древовидной, применение
паттерна может быть избыточным


                       Паттерн "Декоратор" (Decorator)
1) Суть паттерна парой слов:
Декоратор — это структурный паттерн проектирования, который позволяет
динамически добавлять объектам новую функциональность, оборачивая их в
объекты-декораторы. Паттерн представляет гибкую альтернативу наследованию для
расширения возможностей объектов без изменения их кода

2) Проблема, которую решает паттерн:
Проблема 1 — Разрастание иерархии классов при добавлении новых функций:
Предположим, у нас есть базовый класс Notifier, который отправляет уведомления
по email. Мы хотим добавить отправку SMS, Slack-уведомлений, а также комбинации
(например, email + SMS + Slack). Без паттерна придётся создавать классы:
EmailNotifier, SMSNotifier, SlackNotifier, EmailAndSMSNotifier, … и так далее.
Число классов растёт экспоненциально

Проблема 2 — Невозможность динамического изменения поведения объекта:
Если функциональность задается через наследование, то она фиксируется на этапе
компиляции. Нельзя "на лету" добавить новую возможность объекту

Проблема 3 — Нарушение принципа открытости/закрытости:
При добавлении нового типа уведомления придется изменять существующие классы
или создавать новые комбинации

3) Структура паттерна Декоратор:

                  ┌─────────────────────────────────────────┐
                  │                Component                │
                  │           (Базовый компонент)           │
                  ├─────────────────────────────────────────┤
                  │ + operation(): string                   │
                  └────────────────────┬────────────────────┘
                                       │
                 ┌─────────────────────┴───────────────┐
                 │                                     │
                 ▼                                     ▼
    ┌────────────────────────┐           ┌─────────────────────────────┐
    │   ConcreteComponent    │           │          Decorator          │
    │ (Конкретный компонент) │           │         (Декоратор)         │
    ├────────────────────────┤           ├─────────────────────────────┤
    │ + operation(): string  │           │ - component: Component      │
    └────────────────────────┘           ├─────────────────────────────┤
                                         │ + operation(): string       │
                                         └────────────┬────────────────┘
                                                      │
                      ┌───────────────────────────────┴──────┐
                      │                                      │
                      ▼                                      ▼
         ┌─────────────────────────┐            ┌─────────────────────────┐
         │   ConcreteDecoratorA    │            │   ConcreteDecoratorB    │
         │ (Конкретный декоратор)  │            │ (Конкретный декоратор)  │
         ├─────────────────────────┤            ├─────────────────────────┤
         │ + operation(): string   │            │ + operation(): string   │
         │ + addedBehavior(): void │            │ + addedState: string    │
         └─────────────────────────┘            └─────────────────────────┘

Ключевые компоненты:
• Component — определяет интерфейс для объектов, которые могут иметь
добавленную функциональность
• ConcreteComponent — конкретный объект, к которому можно добавлять новую
функциональность
• Decorator — базовый класс декоратора, содержит ссылку на объект Component и
реализует его интерфейс
• ConcreteDecorator — конкретный декоратор, добавляющий новую функциональность.
Может выполнять код до или после вызова метода обернутого объекта

4) Ключевые преимущества паттерна:
• Гибкость расширения — можно динамически добавлять и комбинировать поведения
• Альтернатива наследованию — не требует создания подклассов для каждой
комбинации
• Принцип единой ответственности — каждый декоратор отвечает за одно конкретное
расширение
• Принцип открытости/закрытости — новые декораторы можно добавлять, не изменяя
существующий код
• Прозрачность для клиента — клиент работает с декорированным объектом через
тот же интерфейс

5) Когда применять паттерн?
✓ Когда нужно добавлять обязанности объектам динамически и незаметно для
клиентского кода
✓ Когда нельзя расширить функциональность с помощью наследования
✓ Когда требуется добавлять и снимать дополнительные поведения во время
выполнения программы
✓ Когда нужно реализовать функциональность, которую можно комбинировать
разными способами

6) Важные замечания!
⨯ Сложность отладки — цепочка декораторов может быть длинной, что усложняет
понимание потока выполнения
⨯ Порядок декораторов имеет значение — разные порядки обертывания могут давать
разный результат
⨯ Инициализация декораторов — клиент должен знать о существовании декораторов,
чтобы правильно их создавать
⨯ Множество мелких объектов — каждый декоратор создает новый объект, что может
увеличить потребление памяти
⨯ Не для всех задач — если функциональность статична и не требует комбинаций,
проще использовать наследование


                          Паттерн "Фасад" (Facade)
1) Суть паттерна парой слов:
Фасад — это структурный паттерн проектирования, который предоставляет простой и
унифицированный интерфейс к сложной системе классов, библиотеке или фреймворку.
Фасад скрывает внутреннюю сложность системы, предоставляя клиенту только
необходимые для работы методы, что упрощает использование системы и уменьшает
зависимости между клиентом и её компонентами

2) Проблема, которую решает паттерн:
Проблема 1 — Сложность взаимодействия с многосоставной системой:
Представьте, что для выполнения операции "запустить фильм" в домашнем
кинотеатре нужно: включить проектор, опустить экран, включить аудиосистему,
выключить свет, запустить фильм. Клиенту приходится знать обо всех этих шагах
и выполнять их в правильном порядке

Проблема 2 — Сильная связанность клиента с подсистемами:
Без фасада клиентский код зависит от множества классов подсистемы

Проблема 3 — Частые изменения в подсистеме:
Если изменяется внутренняя структура подсистемы (например, добавляется новый
компонент или меняется порядок инициализации), приходится изменять все
клиентские места, где используется эта подсистема

3) Структура паттерна Фасад:

          ┌─────────────────────────────────────────────────────┐
          │                       Client                        │
          │                      (Клиент)                       │
          └──────────────────────────┬──────────────────────────┘
                                     │
                                     │ использует упрощённый интерфейс
                                     ▼
          ┌─────────────────────────────────────────────────────┐
          │                        Facade                       │
          │                       (Фасад)                       │
          ├─────────────────────────────────────────────────────┤
          │ - subsystemA: SubsystemA                            │
          │ - subsystemB: SubsystemB                            │
          │ - subsystemC: SubsystemC                            │
          ├─────────────────────────────────────────────────────┤
          │ + simpleOperation(): void                           │
          │   // Инкапсулирует сложную логику                   │
          │   simpleOperation() {                               │
          │     subsystemA.operationA();                        │
          │     subsystemB.operationB();                        │
          │     subsystemC.operationC();                        │
          │   }                                                 │
          └──────────────────────────┬──────────────────────────┘
                                     |
             ┌───────────────────────┼───────────────────────┐
             |                       |                       | использует
             ▼                       ▼                       ▼
    ┌─────────────────┐     ┌─────────────────┐     ┌─────────────────┐
    │   SubsystemA    │     │   SubsystemB    │     │   SubsystemC    │
    │  (Подсистема A) │     │  (Подсистема B) │     │  (Подсистема C) │
    ├─────────────────┤     ├─────────────────┤     ├─────────────────┤
    │ + operationA()  │     │ + operationB()  │     │ + operationC()  │
    │ + otherOps()    │     │ + otherOps()    │     │ + otherOps()    │
    └─────────────────┘     └─────────────────┘     └─────────────────┘

Ключевые компоненты:
• Facade (Фасад) — предоставляет упрощённый интерфейс к сложной подсистеме.
Знает, каким классам подсистемы нужно перенаправить запрос клиента
• Subsystem Classes (Классы подсистемы) — реализуют функциональность
подсистемы. Не знают о существовании фасада
• Client (Клиент) — использует фасад для взаимодействия со сложной подсистемой
вместо работы с её классами напрямую

4) Ключевые преимущества паттерна:
• Изоляция сложности — скрывает сложность системы за простым интерфейсом
• Упрощение использования — клиенту нужно знать только один метод фасада вместо
десятков методов подсистемы
• Уменьшение зависимостей — клиент зависит только от фасада, а не от всех
классов подсистемы
• Повышение безопасности — можно ограничить доступ к определённым функциям
подсистемы
• Улучшение поддерживаемости — изменения в подсистеме требуют модификации
только фасада, а не всех клиентов
• Принцип единственной ответственности — фасад отвечает за упрощение работы
с подсистемой

5) Когда применять паттерн?
✓ Когда нужно предоставить простой интерфейс к сложной подсистеме
✓ Когда существует много зависимостей между клиентом и классами реализации
✓ Когда нужно разложить подсистему на отдельные слои — фасад становится точкой
входа для каждого уровня
✓ Когда требуется уменьшить связанность между системами — фасад выступает в
роли «посредника»
✓ Когда нужно скрыть устаревший или сложный код за новым, понятным интерфейсом
✓ Когда необходимо предоставить ограниченный, но достаточный набор функций для
большинства клиентов

6) Важные замечания!
⨯ Может стать "божественным объектом" (God Object) — если фасад начинает
делать слишком много, он превращается в монолитный класс, нарушающий принцип
единственной ответственности
⨯ Ограниченная функциональность — фасад предоставляет только наиболее часто
используемые функции; для доступа к продвинутым возможностям клиенту всё равно
может потребоваться доступ к подсистеме напрямую
⨯ Дополнительный уровень абстракции — добавляет ещё один класс в систему, что
может быть избыточно для простых случаев
⨯ Скрытие возможностей — клиенты могут не знать о некоторых полезных функциях
подсистемы, если они не представлены в фасаде
⨯ Зависимость от внутренней структуры — фасад может стать хрупким, если
внутренняя структура подсистемы часто меняется
⨯ Не заменяет подсистему — фасад лишь упрощает доступ, но не заменяет прямую
работу с подсистемой, когда требуется полный контроль


                    Паттерн "Приспособленец" (Flyweight)
1) Суть паттерна парой слов:
Паттерн "Приспособленец" — это структурный паттерн проектирования, который
позволяет экономить память, разделяя общее состояние между множеством объектов,
вместо хранения одинаковых данных в каждом объекте. Паттерн разделяет данные
на внутреннее состояние (intrinsic), которое неизменно и может быть общим для
многих объектов, и внешнее состояние (extrinsic), которое уникально для каждого
объекта и передаётся в методы при необходимости

2) Проблема, которую решает паттерн:
Проблема 1 — Большое количество объектов потребляет много памяти:
Представьте, что мы разрабатываем текстовый редактор, где каждый символ в
документе представлен объектом. В большом документе могут быть тысячи, а то и
миллионы символов. Если каждый символ хранит свой шрифт, размер, цвет, то объём
памяти становится огромным

// Без паттерна:
class Character {
private:
    char symbol;
    string font;
    int size;
    string color;
    // ... другие свойства
public:
    Character(char s, string f, int sz, string c) 
        : symbol(s), font(f), size(sz), color(c) {}
    // ...
};
// Для документа из 1000 символов создаётся 1000 объектов, каждый со своими
// данными

Проблема 2 — Дублирование одинаковых данных:
В текстовом документе многие символы имеют одинаковые атрибуты. Хранение этих
данных в каждом объекте приводит к избыточности

Проблема 3 — Падение производительности:
Создание и уничтожение большого количества объектов, а также их обработка
требует значительных ресурсов, что может замедлить работу приложения

3) Структура паттерна Приспособленец:

             ┌─────────────────────────────────────────────────────┐
             │                       Client                        │
             │                      (Клиент)                       │
             ├─────────────────────────────────────────────────────┤
             │ - extrinsicState: string[]                          │
             │ + operation(extrinsicState): void                   │
             └──────────────────────────┬──────────────────────────┘
                                        │
                                        │ хранит и передает внешнее состояние
                                        ▼
             ┌─────────────────────────────────────────────────────┐
             │                  FlyweightFactory                   │
             │              (Фабрика приспособленцев)              │
             ├─────────────────────────────────────────────────────┤
             │ - flyweights: Map<string, Flyweight>                │
             ├─────────────────────────────────────────────────────┤
             │ + getFlyweight(key): Flyweight                      │
             │   // Возвращает существующий или создает новый      │
             │   getFlyweight(key) {                               │
             │     if (!flyweights.contains(key)) {                │
             │       flyweights[key] = new ConcreteFlyweight(key); │
             │     }                                               │
             │     return flyweights[key];                         │
             │   }                                                 │
             └──────────────────────────┬──────────────────────────┘
                                        │
                                        │ создает/возвращает
                                        ▼
             ┌─────────────────────────────────────────────────────┐
             │                      Flyweight                      │
             │             (Интерфейс приспособленца)              │
             ├─────────────────────────────────────────────────────┤
             │ + operation(extrinsicState): void                   │
             └──────────────────────────┬──────────────────────────┘
                                        │
                                        │
             ┌──────────────────────────┼──────────────────────────┐
             │                          │                          │
             ▼                          ▼                          ▼
  ┌────────────────────┐  ┌───────────────────────────┐  ┌────────────────────┐
  │ ConcreteFlyweightA │  │ UnsharedConcreteFlyweight │  │ ConcreteFlyweightB │
  │    (разделяемый)   │  │      (неразделяемый)      │  │    (разделяемый)   │
  ├────────────────────┤  ├───────────────────────────┤  ├────────────────────┤
  │ - intrinsicState   │  │ - allState                │  │ - intrinsicState   │
  ├────────────────────┤  ├───────────────────────────┤  ├────────────────────┤
  │ + operation()      │  | + operation()             │  │ + operation()      │
  └────────────────────┘  └───────────────────────────┘  └────────────────────┘

Ключевые компоненты:
• Flyweight (Приспособленец) — интерфейс, через который приспособленцы могут
получать внешнее состояние и действовать на него
• FlyweightFactory (Фабрика приспособленцев) — создает и управляет
приспособленцами. Гарантирует, что приспособленцы разделяются правильно. При
запросе приспособленца фабрика либо возвращает существующий экземпляр, либо
создает новый, если его еще нет
• ConcreteFlyweight (Конкретный приспособленец) — реализует интерфейс Flyweight
и хранит внутреннее состояние (intrinsic state), которое является неизменным
и общим для многих объектов
• UnsharedConcreteFlyweight (Неразделяемый приспособленец) — не все подклассы
Flyweight должны быть разделяемыми. Этот класс представляет объекты, которые
не делят свое состояние
• Client (Клиент) — хранит внешнее состояние (extrinsic state) и передает его
приспособленцам при вызове их методов

4) Ключевые преимущества паттерна:
• Экономия памяти — значительное сокращение использования памяти за счет
разделения общих данных
• Ускорение работы — уменьшение количества создаваемых объектов и нагрузки на
сборщик мусора
• Упрощение системы — клиенты работают с объектами через единый интерфейс, не
заботясь о разделении состояния
• Поддержка большого количества объектов — позволяет работать с системами,
содержащими миллионы объектов, без чрезмерного потребления памяти
• Принцип разделения ответственности — логика разделения состояния вынесена в
фабрику

5) Когда применять паттерн?
✓ Большое количество объектов — когда приложение использует огромное число
объектов, что приводит к высокому потреблению памяти
✓ Наличие повторяющихся данных — когда многие объекты содержат одинаковые
данные, которые можно вынести в общее состояние
✓ Ограниченные ресурсы — при работе в средах с ограниченной памятью
✓ Независимость внешнего состояния — когда внешнее состояние можно вычислить
или передать при вызове методов, а не хранить в объекте
✓ Оптимизация производительности — когда необходимо ускорить работу приложения
за счет уменьшения нагрузки на память и процессор

6) Важные замечания!
⨯ Усложнение кода — вводит дополнительный уровень абстракции и требует
тщательного разделения состояний
⨯ Потенциальные проблемы с многопоточностью — если приспособленцы изменяют
общее состояние, требуется синхронизация
⨯ Сложность отладки — разделение состояния между объектами может затруднить
понимание потока данных
⨯ Не всегда применим — если у объектов мало общих данных или внешнее состояние
слишком велико, выгода от использования паттерна может быть незначительной
⨯ Риск утечки памяти — фабрика хранит все созданные приспособленцы, что может
привести к накоплению объектов, если не предусмотреть механизм их удаления
⨯ Зависимость от клиента — клиент должен правильно управлять внешним
состоянием и передавать его приспособленцам


                        Паттерн "Заместитель" (Proxy)
1) Суть паттерна парой слов:
Заместитель — это структурный паттерн проектирования, который предоставляет
объект-заменитель или суррогат для другого объекта. Заместитель контролирует
доступ к оригинальному объекту, позволяя выполнить какие-либо действия до или
после передачи запроса оригиналу. Паттерн позволяет добавлять дополнительную
логику (кеширование, логирование, контроль доступа) без изменения кода
оригинального объекта

2) Проблема, которую решает паттерн:
Проблема 1 — Прямой доступ к ресурсоемким объектам:
Представьте, что у нас есть объект HeavyDatabase, который загружает большие
объемы данных при инициализации. Если клиент создает этот объект, но использует
его редко, то мы тратим ресурсы впустую

// Прямой доступ - создаем дорогой объект сразу
HeavyDatabase* db = new HeavyDatabase();   // Долгая инициализация
// ... какой-то код ...
db->query("SELECT * FROM users");   // Используем только здесь

Проблема 2 — Необходимость контроля доступа:
Допустим, у нас есть система с разными уровнями доступа. Нужно проверять права
пользователя перед выполнением операций

Document* doc = new Document("secret.txt");
// Любой код может получить доступ к секретному документу!
doc->display();   // Нет проверки прав доступа

Проблема 3 — Распределенные системы и удаленные объекты:
При работе с удаленными объектами (например, через сеть) нужно управлять
сетевым взаимодействием, обработкой ошибок и т.д

3) Структура паттерна Заместитель:

                ┌─────────────────────────────────────┐
                │               Subject               │
                │             (Интерфейс)             │
                ├─────────────────────────────────────┤
                │ + request(): void                   │
                └─────────────────────────────────────┘
                                   ▲ 
                   ┌───────────────┴────────────────────┐
       ┌───────────┴───────────┐         ┌──────────────┴──────────────┐
       │      RealSubject      │         │            Proxy            │
       │   (Реальный объект)   │         │        (Заместитель)        │
       ├───────────────────────┤         ├─────────────────────────────┤
       │ + request(): void     │         │ - realSubject: RealSubject* |
       └───────────────────────┘         │ + request(): void           │
                                         │   // Дополнительная         │
                                         │   // логика до/после        │
                                         │   realSubject->request()    │
                                         └─────────────────────────────┘

Ключевые компоненты:
• Subject (Интерфейс) — определяет общий интерфейс для RealSubject и Proxy
• RealSubject (Реальный объект) — содержит бизнес-логику, к которой требуется
контролируемый доступ
• Proxy (Заместитель) — содержит ссылку на RealSubject, контролирует доступ к
нему, может выполнять дополнительные операции до/после передачи запроса
• Client (Клиент) — работает с объектами через интерфейс Subject, не замечая
разницы между Proxy и RealSubject

4) Ключевые преимущества паттерна:
• Контроль доступа — можно добавлять проверки безопасности, логирование,
кеширование
• Ленивая инициализация — откладывает создание дорогостоящих объектов до
момента их реального использования
• Упрощение клиентского кода — клиент работает с простым интерфейсом, а сложная
логика скрыта в заместителе
• Принцип единственной ответственности — разделение основной логики и
вспомогательных функций (кеширование, логирование и т.д.)
• Принцип открытости/закрытости — можно добавлять новые виды заместителей без
изменения существующего кода
• Прозрачность для клиента — клиент не знает, работает ли он с реальным
объектом или заместителем

5) Когда применять паттерн?
✓ Виртуальный прокси — когда нужно отложить создание ресурсоемкого объекта до
момента его использования
✓ Защищающий прокси — когда требуется контролировать доступ к объекту на
основе прав пользователя
✓ Удаленный прокси — для представления объекта, находящегося в другом адресном
пространстве (удаленный сервис)
✓ Кеширующий прокси — для хранения результатов запросов и их повторного
использования
✓ Логирующий прокси — для записи истории обращения к объекту
✓ Синхронизирующий прокси — для обеспечения потокобезопасного доступа к объекту
✓ Умные ссылки — для подсчета ссылок, блокировки ресурсов, загрузки объектов
по требованию

6) Важные замечания!
⨯ Дополнительный уровень абстракции — вводит дополнительные классы и усложняет
структуру программы
⨯ Задержка выполнения — при наличии дополнительной логики в прокси может
замедляться работа
⨯ Сложность отладки — может быть сложно отследить цепочку вызовов через
несколько уровней прокси
⨯ Риск неправильной реализации — если прокси не полностью имитирует поведение
реального объекта, могут возникнуть ошибки
⨯ Избыточность для простых случаев — не стоит применять, если нет реальной
необходимости в контроле доступа или дополнительной логике
⨯ Проблемы с производительностью — цепочка прокси (декораторы, адаптеры,
прокси) может создать значительный overhead

          Паттерн "Цепочка обязанностей" (Chain of Responsibility)
1) Суть паттерна парой слов:
Цепочка обязанностей — это поведенческий паттерн проектирования, который
позволяет передавать запросы последовательно по цепочке обработчиков. Каждый
обработчик решает, может ли он обработать запрос сам, или нужно передать его
дальше по цепи. Паттерн ослабляет связь между отправителем и получателем
запроса, давая возможность нескольким объектам обработать запрос без явного
указания конкретного обработчика в коде клиента

2) Проблема, которую решает паттерн:
Проблема 1 — Жесткая привязка отправителя к получателю:
Представьте, что мы разрабатываем систему обработки заявок в службе поддержки.
Есть разные уровни поддержки: Level1 (базовые вопросы), Level2 (сложные
проблемы), Level3 (критические ошибки), Level4 (технический директор). Без
паттерна код выглядит так:

if (request.severity == "low") {
    Level1Handler().handle(request);
} else if (request.severity == "medium") {
    Level2Handler().handle(request);
} else if (request.severity == "high") {
    Level3Handler().handle(request);
} else if (request.severity == "critical") {
    Level4Handler().handle(request);
}
// Что делать, если добавится Level5 или изменится логика распределения?

Проблема 2 — Множественные проверки и дублирование кода:
В системах валидации, фильтрации, логирования часто встречается код с длинными
цепочками условных операторов, которые сложно поддерживать и расширять

Проблема 3 — Невозможность динамического изменения порядка обработки:
Без паттерна порядок обработки фиксирован на этапе компиляции. Нельзя "на лету"
изменить последовательность обработчиков, добавить новый шаг посередине или
убрать существующий

3) Структура паттерна Цепочка обязанностей:

                             ┌───────────────────────────────┐
                             │            Handler            │
                             │          (Обработчик)         │
                             ├───────────────────────────────┤
                             │ - next: Handler*              │
                             ├───────────────────────────────┤
                             │ + setNext(Handler*): Handler* │
                             │ + handle(request): void       │
                             └───────────────┬───────────────┘
                                             │
                                             │ наследует
                                             │
              ┌──────────────────────────────┼──────────────────────────────┐
              │                              │                              │
              ▼                              ▼                              ▼
┌───────────────────────────┐  ┌───────────────────────────┐  ┌───────────────────────────┐
│      ConcreteHandler1     │  │      ConcreteHandler2     │  │      ConcreteHandler3     │
│        (Уровень 1)        │  │        (Уровень 2)        │  │        (Уровень 3)        │
├───────────────────────────┤  ├───────────────────────────┤  ├───────────────────────────┤
│ + handle(request): void { │  │ + handle(request): void { │  │ + handle(request): void { │
│     if (canHandle) {      │  │     if (canHandle) {      │  │     if (canHandle)        │
│       process();          │  │       process();          │  │       process();          │
|     }                     |  |     }                     |  |     }                     |
│     else if (next) {      │  │     else if (next) {      │  │     else if (next)        │
│       next->handle();     │  │       next->handle();     │  │       next->handle();     │
│     }                     │  │     }                     │  │     }                     │
| }                         |  | }                         |  | }                         |
└─────────────┬─────────────┘  └─────────────┬─────────────┘  └─────────────┬─────────────┘
              │                              │                              │
              └──────────────────────────────┼──────────────────────────────┘
                                             │
                                             │ формирует цепочку
                                             ▼
                  ┌─────────────────────────────────────────────────────┐
                  │                       Client                        │
                  │                      (Клиент)                       │
                  ├─────────────────────────────────────────────────────┤
                  │ + handler1->setNext(handler2->setNext(handler3)...) │
                  │ + handler1.handle(request)                          │
                  └─────────────────────────────────────────────────────┘

Ключевые компоненты:
• Handler (Обработчик) — интерфейс, который объявляет общий метод handle() для
всех конкретных обработчиков. Обычно содержит ссылку на следующий обработчик
в цепочке
• ConcreteHandler (Конкретный обработчик) — реализует метод handle() в
соответствии со своей логикой. Если обработчик может обработать запрос, он это
делает; если нет — передает запрос дальше по цепочке (если есть следующий)
• Client (Клиент) — формирует цепочку обработчиков (вручную или через фабрику)
и отправляет первый запрос в начало цепочки. Клиент не знает, какой именно
обработчик в итоге обработает запрос

4) Ключевые преимущества паттерна:
• Ослабление связанности — отправитель запроса не знает, какой объект его
обработает. Клиент не зависит от конкретных классов обработчиков
• Гибкость формирования цепочек — можно динамически создавать различные цепочки,
менять порядок обработчиков, добавлять или удалять их во время выполнения
• Принцип единой ответственности — каждый обработчик отвечает только за свою
конкретную логику обработки
• Принцип открытости/закрытости — легко добавлять новые обработчики без
изменения существующего кода
• Управляемая обработка — можно прервать цепочку в любой момент (обработчик
может не вызывать следующий) или, наоборот, гарантировать обработку каждым звеном
• Прозрачность для клиента — клиент отправляет запрос в начало цепочки и не
знает, сколько обработчиков будет задействовано

5) Когда применять паттерн?
✓ Множественные варианты обработки — когда запрос может быть обработан
несколькими объектами, и конкретный обработчик определяется во время выполнения
✓ Неизвестный получатель — когда отправитель не должен знать, какой объект в
итоге обработает запрос
✓ Динамическая цепочка — когда набор и порядок обработчиков должен
формироваться динамически (например, из конфигурационного файла)
✓ Последовательная обработка — когда нужно выполнить несколько операций над
одним запросом в определенном порядке
✓ Условная обработка — когда обработка зависит от типа/свойств запроса, и эти
условия часто меняются
✓ Системы событий — в GUI-фреймворках для обработки событий (клики, нажатия
клавиш), где события всплывают по иерархии компонентов
✓ Валидация данных — последовательная проверка данных разными валидаторами
✓ Системы логирования — логирование с разными уровнями (DEBUG, INFO, ERROR) и
разными обработчиками (консоль, файл, удаленный сервер)
✓ Фильтрация запросов — в веб-фреймворках (middleware, interceptors) для
обработки HTTP-запросов

6) Важные замечания!
⨯ Отсутствие гарантии обработки — запрос может пройти всю цепочку и остаться
необработанным, если ни один обработчик не смог его обработать
⨯ Сложность отладки — цепочки могут быть длинными и формироваться динамически,
что затрудняет отслеживание пути запроса. Особенно сложно, когда обработчики
могут прерывать цепочку в разных местах
⨯ Производительность — каждый запрос проходит через цепочку последовательно.
В длинных цепочках это может создать заметную задержку
⨯ Конфигурация цепочки — ответственность за правильное формирование цепочки
лежит на клиенте. Если забыть связать обработчики, запрос не дойдет до нужного
⨯ Сложность с общей обработкой — иногда нужно, чтобы запрос обработали
несколько обработчиков последовательно (например, логирование + валидация +
сохранение). Паттерн по умолчанию предполагает, что обработку выполняет только
один обработчик, но его можно модифицировать
⨯ Переусложнение — для простых случаев с 2-3 обработчиками создание цепочки
может быть избыточным; проще использовать условный оператор


                         Паттерн "Команда" (Command)
1) Суть паттерна парой слов:
Команда — это поведенческий паттерн проектирования, который превращает запросы
или простые операции в объекты. Паттерн предлагает выносить все детали запроса
(вызываемый метод, параметры, объект-получатель) в отдельный класс-команду.
Это позволяет параметризовать объекты другими объектами, ставить запросы в
очередь, логировать их, а также поддерживать отмену операций

2) Проблема, которую решает паттерн:
Представьте, что мы разрабатываем приложение для текстового редактора с
панелью инструментов и контекстным меню. У нас есть классы кнопок на панели
(ToolbarButton) и пунктов меню (MenuItem). Изначально они выполняют разные
действия: кнопка "Сохранить" сохраняет файл, пункт меню "О программе"
открывает окно "О программе"

Проблема 1 — Жесткая привязка к действиям:
Самый простой способ — заставить кнопку и пункт меню самим знать, что делать.
Класс SaveButton напрямую вызывает метод saveDocument() у какого-то объекта
Document, а класс AboutMenuItem вызывает showAboutDialog(). Это создает жесткую
связь. Что, если мы захотим изменить действие кнопки "Сохранить"? Придется
менять код в классе SaveButton

Проблема 2 — Дублирование кода:
Если у нас есть несколько способов вызвать одно и то же действие, то логика
сохранения будет дублироваться в трех разных местах

Проблема 3 — Невозможность реализовать продвинутые функции:
Без паттерна мы не можем легко реализовать отмену операций (Undo), историю
операций (Logging), очереди задач (Queueing)

3) Структура паттерна Команда:

                     ┌─────────────────────────────────────┐
                     │               Command               │

Ключевые компоненты:
• Command (Интерфейс команды): Объявляет интерфейс для выполнения операции.
Обычно содержит метод execute(). Для поддержки отмены добавляется метод undo()
• ConcreteCommand (Конкретная команда): Класс, реализующий интерфейс Command.
Хранит ссылку на объект-получатель (receiver) и параметры, необходимые для
вызова его метода. В методе execute() он вызывает нужный метод у получателя
• Receiver (Получатель): Класс, который содержит непосредственную бизнес-логику
выполнения операции. Это тот объект, над которым на самом деле производятся
действия (документ, база данных, приложение)
• Invoker (Вызывающий / Инициатор): Класс, который хранит команду и инициирует
ее выполнение. Он не знает ничего о конкретной команде, кроме того, что она
реализует интерфейс Command
• Client (Клиент): Создает объекты конкретных команд, связывая их с конкретными
получателями. Затем он передает эти команды вызывающим объектам

4) Ключевые преимущества паттерна:
• Отделение инициатора от получателя — Класс, который вызывает операцию, ничего
не знает о том, кто ее выполняет. Это ослабляет связанность
• Принцип единой ответственности — Каждая команда отвечает за конкретное
действие. Можно изменять логику команды, не затрагивая инициатора или
получателя
• Принцип открытости/закрытости — В систему можно легко добавлять новые
команды, не изменяя существующие классы инициаторов
• Параметризация объектов — Можно создавать команды с разными параметрами и
передавать их в один и тот же инициатор
• Поддержка отмены операций — Команды могут хранить состояние, необходимое для
отката своих действий. Реализовав метод undo(), можно легко создать историю
команд для отмены/повтора
• Возможность отложенного выполнения — Команды можно складывать в очередь,
выполнять по расписанию или в фоновом потоке
• Возможность логирования и транзакций — Можно легко записывать все выполненные
команды в лог или группировать их в транзакции

5) Когда применять паттерн?
✓ Когда нужно передавать операции в качестве аргументов другим объектам
✓ Когда нужно организовывать выполнение операций в очередь или по расписанию
✓ Когда необходимо вести лог всех выполненных операций для последующего анализа
или восстановления
✓ Когда нужна поддержка отмены операций (Undo/Redo)
✓ Когда группа операций должна быть выполнена либо целиком, либо не выполнена
вовсе

6) Важные замечания!
⨯ Усложнение кода — Паттерн вводит множество дополнительных классов. Для
простых действий с одним получателем это может быть избыточно
⨯ Увеличение количества классов — На каждое новое действие придется создавать
новый класс команды
⨯ Сложность реализации отмены — Для полноценной поддержки отмены, команды
должны хранить достаточно информации о своем предыдущем состоянии или уметь
выполнять обратное действие. Это может быть нетривиально для сложных операций
⨯ Взаимодействие с получателем — Команда должна знать своего получателя. Это
все еще зависимость, хотя и гораздо более слабая, чем прямая зависимость
инициатора от получателя


                    Паттерн "Интерпретатор" (Interpreter)
1) Суть паттерна парой слов:
Интерпретатор — это поведенческий паттерн проектирования, который определяет
представление грамматики для заданного языка и предоставляет интерпретатор для
обработки предложений этого языка. Паттерн реализуется путем создания классов
для каждого символа (правила) грамматики (терминальных и нетерминальных
выражений), а предложение языка представляется в виде абстрактного
синтаксического дерева (AST), построенного из экземпляров этих классов

2) Проблема, которую решает паттерн:
Представьте, что мы разрабатываем программу для работы с поисковыми запросами.
Пользователь может вводить сложные выражения, например: "кот" ИЛИ ("собака" И
"щенок"). Нам нужно разобрать эту строку, понять структуру запроса и выполнить
поиск

Проблема 1 — Сложность разбора и выполнения:
Как преобразовать строку "кот" ИЛИ ("собака" И "щенок") в понятный для
программы алгоритм поиска? Простое строковое сравнение не сработает, нужно
учитывать логику операторов И и ИЛИ, а также приоритет скобок

Проблема 2 — Нарушение принципа открытости/закрытости:
Если грамматика языка проста (например, только оператор И), логику разбора и
выполнения можно написать в одном методе. Но если мы захотим добавить новые
операторы (НЕ, ИЛИ, скобки), нам придется постоянно изменять и усложнять этот
метод, что приведет к появлению множества условных операторов и сделает код
хрупким

Проблема 3 — Отсутствие структурированного представления:
Без паттерна у нас не будет формальной модели, представляющей структуру
запроса. Каждый раз, когда нужно выполнить новую операцию над запросом
(например, не выполнить, а подсчитать количество условий или преобразовать
в другой формат), нам пришлось бы заново писать логику разбора строки

3) Структура паттерна Интерпретатор:

                         ┌───────────────────────────────┐
                         │      AbstractExpression       │
                         │    (Абстрактное выражение)    │
                         ├───────────────────────────────┤
                         │ + interpret(context): void    │
                         └───────────────┬───────────────┘
                                         │
             ┌───────────────────────────┼──────────────────────────┐
             │                           │                          │

                      ┌─────────────────────────────────────┐

                      ├─────────────────────────────────────┤

Ключевые компоненты:
• AbstractExpression (Абстрактное выражение): Интерфейс, объявляющий метод
interpret(), общий для всех узлов абстрактного синтаксического дерева (AST).
Обычно принимает объект Context, содержащий глобальную информацию для
интерпретации
• TerminalExpression (Терминальное выражение): Представляет правило грамматики,
которое не может быть разложено на более простые составляющие (например,
ключевое слово или переменная). Реализует операцию interpret() для этого
конечного элемента
• NonterminalExpression (Нетерминальное выражение): Представляет сложное
правило грамматики, которое состоит из других выражений (терминальных или
нетерминальных). Например, выражение для операций И или ИЛИ. Его метод
interpret() обычно рекурсивно вызывает interpret() для своих составных частей
(left и right), а затем комбинирует результаты
• Context (Контекст): Содержит информацию, глобальную для интерпретатора. В
нашем примере с поиском, контекст может хранить множество документов, по
которым идет поиск, или маппинг переменных на их значения
• Client (Клиент): Строит абстрактное синтаксическое дерево (AST),
представляющее конкретное предложение языка на данном этапе. Затем клиент
вызывает метод interpret() для корневого узла дерева, передавая ему объект
Context

4) Ключевые преимущества паттерна:
• Простота изменения и расширения грамматики — Чтобы изменить или расширить
язык, достаточно изменить или добавить соответствующие классы выражений, следуя
принципу открытости/закрытости
• Легкость реализации грамматики — Классы для каждого правила грамматики имеют
четкую структуру и небольшую зону ответственности, что упрощает реализацию и
понимание
• Грамматика, управляемая объектами — Сама структура классов (AST) является
представлением грамматики, что делает код более выразительным
• Разделение грамматики и интерпретации — Классы выражений отвечают только за
структуру, а логика интерпретации (выполнения) заключена в их методах

5) Когда применять паттерн?
✓ Когда нужно интерпретировать выражения на простом языке — Например,
математические выражения, логические условия, простые языки запросов (как в
примере с поиском), конфигурационные файлы
✓ Когда грамматика языка проста и стабильна — Паттерн становится громоздким для
очень сложных грамматик. В таких случаях лучше использовать специализированные
генераторы парсеров (например, ANTLR, Yacc)
✓ Когда важна производительность, а дерево разбора невелико — Хотя
интерпретация через AST может быть не самой быстрой, для небольших выражений
это приемлемо
✓ Когда в приложении повторяется одна и та же задача интерпретации — Например,
расчет формул в электронной таблице, проверка бизнес-правил, описанных на
внутреннем DSL (Domain-Specific Language)

6) Важные замечания!
⨯ Сложность поддержки сложных грамматик — Для языков с большим количеством
правил (10+) паттерн приводит к созданию огромного числа маленьких классов,
что делает систему труднообозримой
⨯ Низкая производительность — Рекурсивный обход AST для каждого выражения может
быть медленным, особенно если дерево глубокое. Это основной недостаток
⨯ Сложность управления контекстом — Передача и обновление состояния в объекте
Context может быть нетривиальной задачей, особенно при наличии вложенных
областей видимости
⨯ Не заменяет полноценные парсеры — Интерпретатор это паттерн для простых
языков. Для сложных языков программирования или файлов конфигурации со сложной
структурой он не подходит


                        Паттерн "Итератор" (Iterator)
1) Суть паттерна парой слов:
Итератор — это поведенческий паттерн проектирования, который предоставляет
способ последовательного доступа ко всем элементам составного объекта
(например, списка, множества или дерева), не раскрывая его внутреннего
представления. Паттерн выносит поведение обхода коллекции из самой коллекции
в отдельный класс-итератор, что позволяет использовать разные стратегии обхода
и иметь несколько активных обходов одновременно

2) Проблема, которую решает паттерн:
Представьте, что у нас есть различные типы коллекций: ArrayList, LinkedList,
TreeSet, HashSet. Каждая из них хранит элементы по-своему

Проблема 1 — Разный интерфейс обхода:
Как клиенту перебрать все элементы каждой коллекции? Без паттерна клиент
должен знать внутреннюю структуру каждой коллекции. Это приводит к тому, что
клиентский код жестко привязывается к конкретным типам коллекций и способам
обхода

Проблема 2 — Нарушение инкапсуляции:
Если бы мы захотели реализовать обход нашего собственного TreeSet (двоичного
дерева) в глубину (DFS) или в ширину (BFS), нам пришлось бы добавлять эти
методы прямо в класс коллекции. Это сделало бы класс коллекции слишком сложным
и "раздутым". Более того, у нас не может быть двух одновременных обходов одного
и того же дерева разными способами, так как состояние обхода хранилось бы в
полях самой коллекции

Проблема 3 — Ограниченность обхода:
Стандартные циклы не позволяют легко приостановить обход, возобновить его позже
или обходить элементы в обратном порядке, не меняя код самой коллекции

3) Структура паттерна Итератор:

                        ┌─────────────────────────────────────┐
                        │            Aggregate<T>             │
                        │       (Абстрактная коллекция)       │
                        ├─────────────────────────────────────┤
                        │ + createIterator(): Iterator<T>     │
                        └──────────────────┬──────────────────┘
                                           │
                                           │ создает
                       ┌───────────────────┴───────────────────┐
                       │                                       │
                       ▼                                       ▼
  ┌────────────────────────────────────────┐    ┌─────────────────────────────┐
  │          ConcreteAggregate<T>          │    │         Iterator<T>         │
  │         (Конкретная коллекция)         │    │         (Итератор)          │
  ├────────────────────────────────────────┤    ├─────────────────────────────┤
  │ - data: vector<T>                      │    │ + hasNext(): bool           │
  ├────────────────────────────────────────┤    │ + next(): T                 │
  │ + createIterator(): Iterator {         │    └──────────────┬──────────────┘
  │     return new ConcreteIterator(this); |                   | реализует
  |   }                                    |                   |
  └────────────────────────────────────────┘                   │
                                                               |
                                        ┌──────────────────────┘
                                        |
                    ┌───────────────────┴──────────────────┐
                    │                                      │
                    ▼                                      ▼
   ┌─────────────────────────────────┐    ┌─────────────────────────────────┐
   │         ConcreteIterator        │    │         ConcreteIterator        │
   │      (Итератор по порядку)      │    │  (Итератор в обратном порядке)  │
   ├─────────────────────────────────┤    ├─────────────────────────────────┤
   │ - aggregate: ConcreteAggregate* │    │ - aggregate: ConcreteAggregate* |
   │ - cursor: int                   │    │ - cursor: int                   │
   ├─────────────────────────────────┤    ├─────────────────────────────────┤
   │ + hasNext(): bool               │    │ + hasNext(): bool               │
   │ + next(): T                     │    │ + next(): T                     │
   └─────────────────────────────────┘    └─────────────────────────────────┘

Ключевые компоненты:
• Aggregate (Агрегат): Интерфейс коллекции, который объявляет метод для
создания итератора (createIterator)
• ConcreteAggregate (Конкретная коллекция): Класс, который хранит данные и
возвращает правильный итератор для самого себя
• Iterator (Итератор): Интерфейс, который определяет методы для обхода
коллекции. Обычно это hasNext() (проверяет, есть ли еще элементы для обхода)
и next() (возвращает текущий элемент и переходит к следующему)
• ConcreteIterator (Конкретный итератор): Реализует логику обхода конкретной
коллекции. Хранит текущую позицию обхода (cursor). Для одной коллекции может
быть несколько конкретных итераторов (прямой, обратный, фильтрующий)

4) Ключевые преимущества паттерна:
• Единообразный интерфейс обхода — Клиент может перебирать элементы любых
коллекций (списки, деревья, множества) с помощью одного и того же набора
методов (hasNext, next)
• Скрытие сложности реализации — Клиенту не нужно знать, как устроена коллекция
внутри (массив, связный список, дерево). Итератор берет всю работу на себя
• Инкапсуляция логики обхода — Алгоритмы обхода выносятся из классов данных в
отдельные классы, что упрощает и коллекции, и итераторы
• Несколько активных обходов — Можно создавать несколько итераторов для одной
коллекции, и каждый будет хранить свое собственное состояние (текущую позицию),
позволяя обходить коллекцию одновременно разными способами
• Принцип единой ответственности — Коллекция отвечает за хранение данных,
итератор — за их обход
• Принцип открытости/закрытости — Можно добавлять новые типы коллекций и новые
стратегии обхода, не изменяя существующий код клиента или коллекций

5) Когда применять паттерн?
✓ Когда у нас есть сложная структура данных, и мы хотим скрыть детали её
реализации от клиента, предоставив ему простой интерфейс для перебора
элементов
✓ Когда нам нужно иметь несколько активных обходов одной и той же коллекции
✓ Когда нам нужно предоставить универсальный интерфейс для перебора различных
типов коллекций (полиморфизм)
✓ Когда нам нужны разные способы обхода одной и той же коллекции (например,
прямой, обратный, обход только четных элементов), и мы не хотим "засорять"
класс коллекции этими методами

6) Важные замечания!
⨯ Усложнение для простых коллекций — Для простого списка или массива создание
отдельного класса итератора может быть избыточным
⨯ Прямая модификация коллекции — Если во время обхода итератором коллекция
изменяется (добавляются или удаляются элементы), итератор может сломаться
⨯ Небольшое падение производительности — По сравнению с простым циклом for,
использование итератора вносит небольшой overhead из-за вызова виртуальных
методов, но в современном программировании этим обычно пренебрегают


                       Паттерн "Посредник" (Mediator)
1)Суть паттерна парой слов:
Посредник — это поведенческий паттерн проектирования, который уменьшает
связанность между множеством взаимодействующих объектов. Паттерн вводит
объект-посредник, который инкапсулирует в себе логику взаимодействия между
этими объектами. Вместо того чтобы объекты общались напрямую, они обращаются
к посреднику, который перенаправляет их вызовы соответствующим получателям.
Это превращает хаотичную сеть связей "многие-ко-многим" в упорядоченную
структуру "один-ко-многим"

2)Проблема, которую решает паттерн:
Представьте, что мы разрабатываем приложение для управления полетами в
аэропорту. У нас есть множество объектов: ВзлетныеПолосы (Runway), Самолеты
(Aircraft), ДиспетчерскаяВышка (ControlTower), СлужебныеАвтомобили
(ServiceVehicle), Метеостанция (WeatherStation)

Проблема 1 — Сильная связанность (Спагетти-код):
Каждый объект должен знать о множестве других, чтобы правильно функционировать.
Самолету нужно знать состояние полосы, разрешение от вышки, предупреждения от
служб. Служебной машине нужно избегать столкновений с самолетами. Это создает
запутанную сеть зависимостей, где изменение в одном классе (например,
добавление нового типа транспорта) может повлечь за собой изменения во всех
классах, которые с ним взаимодействуют

Проблема 2 — Сложность повторного использования:
Класс Самолета, жестко завязанный на конкретную реализацию ДиспетчерскойВышки
и правил конкретного аэропорта, невозможно будет использовать в другом проекте
или даже в другом аэропорту с иными правилами

Проблема 3 — Невозможность централизованного управления:
Логика координации (например, правило "самолет не может выруливать на полосу,
если на ней есть машина") размазана по всем классам. Чтобы изменить это
правило, нам пришлось бы редактировать код и Самолета, и Автомобиля, и Полосы.
Это крайне неудобно и чревато ошибками

Проблема 4 — Лавинообразные изменения:
Без паттерна, при добавлении нового участника (например, "Дрон-доставщик"), нам
пришлось бы добавлять ссылки на него во все существующие классы, с которыми он
может взаимодействовать

3)Структура паттерна Посредник:

            ┌─────────────────────────────────────────────────────┐
            │                       Mediator                      │
            │                     (Посредник)                     │
            ├─────────────────────────────────────────────────────┤
            │ + notify(sender: Colleague, event: string): void    │
            └─────────────────────────────────────────────────────┘
                                       ▲
                                       │ реализует
                     ┌─────────────────┴─────────────────┐
        ┌────────────┴───────────┐          ┌────────────┴───────────┐
        │    ConcreteMediatorA   │          │    ConcreteMediatorB   │
        │ (Конкретный посредник) │          │ (Конкретный посредник) │
        ├────────────────────────┤          ├────────────────────────┤
        │ - colleagues           │          │ - colleagues           │
        │ + notify(...)          │          │ + notify(...)          │
        └────────────┬───────────┘          └────────────┬───────────┘
                     |                                   |
                     │    управляет и взаимодействует    |
                     ▼                                   ▼
      ┌─────────────────────────────────────────────────────────────────┐
      │                            Colleague                            │
      │                            (Коллега)                            │
      ├─────────────────────────────────────────────────────────────────┤
      │ - mediator: Mediator*                                           │
      ├─────────────────────────────────────────────────────────────────┤
      │ + Colleague(mediator)                                           │

 │      (Самолет)     │     │  (ВзлетнаяПолоса)  │     │    (Автомобиль)    │
 ├────────────────────┤     ├────────────────────┤     ├────────────────────┤
 │ + receive(event)   │     │ + receive(event)   │     │ + receive(event)   │
 └────────────────────┘     └────────────────────┘     └────────────────────┘

Ключевые компоненты:
• Mediator (Посредник): Интерфейс, определяющий метод для связи с
объектами-коллегами (обычно notify или send)
• ConcreteMediator (Конкретный посредник): Реализует интерфейс Посредника и
координирует взаимодействие между объектами-коллегами. Он знает всех коллег и
их роли, а также содержит всю логику их взаимодействия
• Colleague (Коллега): Базовый интерфейс или абстрактный класс для всех
компонентов, которые взаимодействуют через посредника. Каждый коллега хранит
ссылку на объект посредника
• ConcreteColleague (Конкретный коллега): Конкретные классы компонентов. Они не
общаются друг с другом напрямую. Когда коллеге нужно сообщить о каком-то
событии, он вызывает метод send или notify у посредника, передавая себя и
информацию о событии. Посредник сам решает, кому и как перенаправить это
сообщение

4) Ключевые преимущества паттерна:
• Уменьшение связанности — Классы коллег не имеют прямых ссылок друг на друга.
Они зависят только от одного абстрактного интерфейса — Mediator. Это превращает
сложные связи "многие-ко-многим" в простую связь "один-ко-многим"
• Централизация управления — Вся логика взаимодействия вынесена в одно место —
конкретный посредник. Это упрощает понимание, поддержку и изменение правил
коммуникации
• Упрощение классов коллег — Коллеги становятся проще, так как их единственная
задача — выполнять свою прямую функцию и уведомлять посредника о своих
событиях. Им не нужно знать, как их действия повлияют на остальную систему
• Принцип открытости/закрытости — Можно добавлять новых коллег, не изменяя
существующих. Достаточно создать новый класс коллеги и обновить логику в
конкретном посреднике (или создать нового посредника)
• Повышение переиспользуемости — Отдельные классы коллег становятся независимыми
и могут быть легко использованы в других контекстах с другими посредниками

5) Когда применять паттерн?
✓ Когда несколько объектов общаются между собой сложным и запутанным образом,
что приводит к нечитаемым и трудно поддерживаемым связям
✓ Когда трудно изменять классы, потому что они тесно связаны с множеством
других классов
✓ Когда логика взаимодействия должна быть гибкой и легко изменяемой (например,
правила бизнес-процесса)
✓ Когда нужно переиспользовать отдельные компоненты в других системах, но для
этого их приходится "отрывать" от их текущего окружения
✓ Когда взаимодействие между компонентами настолько сложное, что его выгодно
вынести в отдельный класс для упрощения архитектуры

6) Важные замечания!
⨯ Риск создания "Божественного объекта" (God Object) — Если в посредник
перенести слишком много логики, он может превратиться в монолитный класс,
который знает и делает всё, что нарушает принцип единой ответственности.
Важно следить, чтобы посредник только координировал, а не выполнял работу за
коллег
⨯ Потенциальное узкое место — Поскольку все коммуникации проходят через
посредника, он может стать узким местом в производительности системы, особенно
если обмен сообщениями очень интенсивный
⨯ Усложнение структуры — Введение дополнительного уровня абстракции может быть
избыточным для простых взаимодействий, где прямой обмен между 2-3 объектами
был бы понятнее и проще


                        Паттерн "Хранитель" (Memento)
1) Суть паттерна парой слов:
Хранитель — это поведенческий паттерн проектирования, который позволяет
выносить внутреннее состояние объекта за его пределы для последующего
восстановления, не нарушая инкапсуляцию. Паттерн создает объект-«снимок»
(хранитель), который содержит всю необходимую информацию о состоянии
объекта-создателя (originator). Этот снимок можно хранить в специальном
«опекуне» (caretaker), который управляет историей состояний, но не может
изменять содержимое самих снимков

2) Проблема, которую решает паттерн:
Представьте, что мы разрабатываем текстовый редактор с функцией «Отмена»
Пользователь может вводить текст, форматировать его, и ему нужно иметь
возможность откатывать изменения назад

Проблема 1 — Нарушение инкапсуляции для реализации истории:
Самый простой способ реализовать «Отмену» — сохранять состояние объекта
редактора перед каждым действием. Но как получить это состояние? Можно сделать
все поля публичными, но тогда любой другой код сможет их менять, что нарушит
инкапсуляцию

Проблема 2 — Сложность восстановления приватного состояния:
Можно попробовать реализовать функцию saveState() и restoreState() внутри
самого редактора. Но тогда ответственность за хранение истории (списка
состояний) ложится на редактор, что нарушает принцип единой ответственности.
Редактор должен редактировать текст, а не управлять списком отмен

Проблема 3 — Жесткая связь между редактором и историей:
Если мы вынесем список состояний в отдельный класс History, ему все равно
потребуется доступ к внутренностям редактора, чтобы скопировать их. Это либо
снова приводит к нарушению инкапсуляции, либо к созданию громоздких
методов-«обдирщиков» в редакторе

3) Структура паттерна Хранитель:

          ┌─────────────────────────────────────────────────────┐
          │                      Originator                     │
          │                     (Создатель)                     │
          ├─────────────────────────────────────────────────────┤
          │ - state: string                                     │
          │ - privateField: int                                 │
          ├─────────────────────────────────────────────────────┤
          │ + doSomething(): void                               │
          │ + save(): Memento*                                  │
          │ + restore(m: Memento*): void                        │
          └──────────────────────────┬──────────────────────────┘
                                     │
                                     │ создает и восстанавливается из
                                     ▼
          ┌─────────────────────────────────────────────────────┐
          │                       Memento                       │
          │                     (Хранитель)                     │
          ├─────────────────────────────────────────────────────┤
          │ - state: string  // внутреннее состояние            │
          ├─────────────────────────────────────────────────────┤
          │ + getState(): string                                │
          │ + getName(): string                                 │
          └──────────────────────────┬──────────────────────────┘
                                     │
                                     │ хранит и управляет
                                     ▼
          ┌─────────────────────────────────────────────────────┐
          │                      Caretaker                      │
          │                       (Опекун)                      │
          ├─────────────────────────────────────────────────────┤
          │ - history: Stack<Memento*>                          │
          ├─────────────────────────────────────────────────────┤
          │ + undo(): void {                                    │
          │     if (!history.empty()) {                         │
          │         originator->restore(history.top());         │
          │         history.pop();                              │
          │     }                                               │
          │ }                                                   │
          └─────────────────────────────────────────────────────┘

Ключевые компоненты:
• Originator (Создатель): Объект, состояние которого нужно сохранять. Он умеет
создавать объект Memento (снимок своего состояния) и восстанавливать свое
состояние из полученного снимка
• Memento (Хранитель): «Снимок» состояния создателя. Этот объект — неизменяемый
(immutable) для внешнего мира. Он отдает данные только тому объекту, который
его создал
• Caretaker (Опекун): Управляет историей снимков. Он может сохранять снимки
(push), запрашивать отмену (pop), но никогда не изменяет содержимое самого
снимка. Опекун работает со снимком только как с «черным ящиком» (например,
может хранить его название или дату создания)

4) Ключевые преимущества паттерна:
• Сохранение инкапсуляции — Внутреннее состояние объекта остается приватным.
Никто, кроме самого создателя, не имеет доступа к внутренностям снимка
• Упрощение создателя — Код создания и восстановления состояния находится в
самом создателе (что логично), но ответственность за хранение истории
делегируется опекуну
• Принцип единой ответственности — Originator отвечает за бизнес-логику,
Memento — за хранение среза состояния, Caretaker — за управление историей
• Простота реализации Undo/Redo — Паттерн предоставляет естественную
архитектуру для реализации функций отмены и повтора действий
• Надежность — Состояние объекта восстанавливается атомарно из снимка, что
исключает возможность «частичного» восстановления

5) Когда применять паттерн?
✓ Функции Undo (Отмена) и Redo (Повтор) — Это классический пример
использования. Текстовые редакторы, графические редакторы, CAD-системы
✓ Транзакции — Когда нужно выполнить операцию с возможностью отката к
исходному состоянию в случае ошибки
✓ Создание контрольных точек (Checkpoints/Snapshots) — В играх (сохранение
прогресса перед битвой с боссом), в приложениях с долгими вычислениями
(сохранение промежуточных результатов)
✓ Сериализация внутреннего состояния — Когда нужно сохранить состояние объекта
в файл или БД, не раскрывая его структуру

6) Важные замечания!
⨯ Потребление памяти (Overhead) — Если состояние создателя очень большое,
хранение каждого снимка в памяти приведет к быстрому исчерпанию ресурсов
⨯ Сложность с глубоким копированием — Если состояние создателя содержит ссылки
на другие сложные объекты, создание снимка может потребовать реализации
глубокого копирования всей структуры объектов
⨯ Уязвимость «дешевых» снимков — В языках без строгого контроля доступа
(например, Python) любопытный опекун теоретически мог бы заглянуть в снимок и
попытаться его изменить
⨯ Избыточность — Для простых объектов с 2-3 полями, где история не нужна,
паттерн создает лишнюю сложность


                      Паттерн "Наблюдатель" (Observer)
1) Суть паттерна парой слов:
Наблюдатель — это поведенческий паттерн проектирования, который создает
механизм подписки, позволяющий одним объектам (наблюдателям) следить и
реагировать на события, происходящие в других объектах (субъектах). Паттерн
определяет зависимость "один-ко-многим" между объектами, так что при изменении
состояния одного объекта все зависящие от него оповещаются об этом и
автоматически обновляются. Субъект "рассылает" уведомления, не зная ничего о
конкретных наблюдателях, кроме того, что они реализуют общий интерфейс

2) Проблема, которую решает паттерн:
Представьте, что мы разрабатываем биржевое приложение. У нас есть класс
StockData (данные об акциях), который получает обновления цен из внешнего
источника. Также у нас есть несколько визуальных элементов: StockChart (график
цен), PriceDisplay (табло с текущей ценой), NewsTicker (бегущая строка с
новостями об этой акции)

Проблема 1 — Жесткая связь и "пассивное" получение данных:
Самый простой, но плохой способ — заставить StockData самому обновлять все
визуальные элементы при каждом изменении цены. Это создает жесткую связь.
StockData вынужден знать о всех конкретных классах, которые зависят от его
данных. Добавление нового элемента (например, AIAnalyst) потребует изменения
класса StockData. Это нарушает принцип открытости/закрытости

Проблема 2 — Необходимость "активного" опроса (Pull):
Альтернативный подход — заставить визуальные элементы постоянно (например,
каждую секунду) спрашивать у StockData: "А цена изменилась?". Это называется
активным опросом (polling). Это крайне неэффективно: большая часть запросов
будет бесполезной (данные не изменились), что приводит к бесполезной трате
процессорного времени и создает задержки в обновлении интерфейса

Проблема 3 — Сложность поддержки и масштабирования:
Без паттерна любое изменение логики уведомлений (например, уведомлять не всех
сразу, а с приоритетом) приводит к каскадным изменениям во всех связанных
классах. Система становится монолитной и хрупкой

3) Структура паттерна Наблюдатель:

               ┌─────────────────────────────────────┐
               │               Subject               │
               │              (Субъект)              │
               ├─────────────────────────────────────┤
               │ + attach(Observer)                  │
               │ + detach(Observer)                  │
               │ + notify()                          │
               └─────────────────────────────────────┘
                                  ▲
                                  │ реализует
                                  |
              ┌───────────────────┴───────────────────┐
  ┌───────────┴───────────┐               ┌───────────┴───────────┐
  │    ConcreteSubject    │               │       Observer        │
  │ (Конкретный субъект)  │               │     (Наблюдатель)     │
  ├───────────────────────┤               ├───────────────────────┤
  │ - observers: List     │               │ + update()            │
  │ - state: State        │               └───────────────────────┘
  ├───────────────────────┤                           ▲
  │ + getState(): State   │                           | реализует
  │ + setState(State)     │                           │
  │ + notify()            │                ┌──────────┘
  └───────────────────────┘                │
                                           |
                         ┌─────────────────┴────────────────┐
          ┌──────────────┴─────────────┐      ┌─────────────┴──────────────┐
          │      ConcreteObserverA     │      │      ConcreteObserverB     │
          │  (Конкретный наблюдатель)  │      │  (Конкретный наблюдатель)  │
          ├────────────────────────────┤      ├────────────────────────────┤
          │ - subject: ConcreteSubject │      │ - subject: ConcreteSubject │
          │ - observerState: State     │      │ - observerState: State     │
          ├────────────────────────────┤      ├────────────────────────────┤
          │ + update()                 │      │ + update()                 │
          └────────────────────────────┘      └────────────────────────────┘

Ключевые компоненты:
• Subject (Субъект): Интерфейс или абстрактный класс, который определяет
методы для управления подпиской (attach, detach) и метод уведомления (notify).
Субъект не знает конкретных наблюдателей, только то, что они реализуют
интерфейс Observer
• ConcreteSubject (Конкретный субъект): Хранит непосредственно интересующие
наблюдателей данные (subjectState). При изменении своего состояния он вызывает
унаследованный метод notify(), который оповещает всех подписанных наблюдателей
• Observer (Наблюдатель): Интерфейс, который определяет метод update(). Этот
метод будет вызываться субъектом для оповещения об изменении
• ConcreteObserver (Конкретный наблюдатель): Реализует интерфейс Observer.
Хранит ссылку на конкретного субъекта (чтобы при необходимости запросить его
состояние) и свое собственное состояние, которое должно быть синхронизировано
с состоянием субъекта. В методе update() он получает актуальные данные и
обновляет свое состояние/отображение

4) Ключевые преимущества паттерна:
• Слабая связанность (Loose Coupling) — Субъект ничего не знает о конкретных
классах наблюдателей. Он зависит только от абстрактного интерфейса Observer.
Это позволяет независимо развивать и изменять как субъект, так и наблюдателей
• Поддержка широковещательных уведомлений — Субъект автоматически оповещает
всех подписанных наблюдателей, не заботясь об их количестве. Наблюдатели можно
добавлять или удалять в любой момент
• Принцип открытости/закрытости — Можно вводить новых наблюдателей, не изменяя
код субъекта. Достаточно создать новый класс, реализующий интерфейс Observer,
и подписать его
• Динамические связи — Программа может управлять списком наблюдателей во время
выполнения, подписывая и отписывая их в зависимости от условий

5) Когда применять паттерн?
✓ Когда изменение состояния одного объекта требует изменения других объектов,
и набор этих объектов заранее неизвестен или может динамически меняться
✓ Когда одни объекты должны наблюдать за другими, но только на определенное
время или в определенном контексте
✓ Когда необходимо реализовать механизм рассылки уведомлений, не создавая
жестких зависимостей между отправителем и получателями

6) Важные замечания!
⨯ Неожиданные обновления — Последовательность уведомлений может быть
непредсказуемой для наблюдателей, если субъект не гарантирует определенный
порядок вызова update()
⨯ Сложность отладки — При большом количестве наблюдателей и сложных цепочках
обновлений поток выполнения программы становится трудно отследить
⨯ Утечки памяти — Если наблюдатель подписался на субъекта, но забыл отписаться
(detach) перед своим удалением, субъект продолжит хранить ссылку на него. Это
не даст сборщику мусора удалить наблюдателя, что приведет к утечке памяти
⨯ Производительность — Серия последовательных уведомлений может быть медленной,
особенно если наблюдатели выполняют тяжелые операции в методе update(). Если
уведомления происходят очень часто, это может создать нагрузку на систему


                         Паттерн "Состояние" (State)
1) Суть паттерна парой слов:
Состояние — это поведенческий паттерн проектирования, который позволяет объекту
изменять свое поведение в зависимости от внутреннего состояния. Создается
впечатление, что объект поменял свой класс. Паттерн предлагает вынести логику
состояния в отдельные классы, а исходный объект (контекст) делегирует
выполнение своих задач текущему объекту-состоянию, вместо того чтобы
реализовывать все возможные варианты поведения самостоятельно с помощью
условных операторов

2) Проблема, которую решает паттерн:
Представьте, что мы разрабатываем приложение для онлайн-заказа еды. Заказ может
находиться в разных статусах: «Новый», «Оплачен», «Отправлен», «Доставлен» или
«Отменен». В каждом статусе поведение заказа разное. Например, метод отменить()
должен работать только для заказов в статусе «Новый» или «Оплачен», но не для
«Доставлен»

Проблема 1 — Огромные условные операторы (God Object):
Самое очевидное, но плохое решение — реализовать все возможное поведение в
одном классе Order, используя переменную status и операторы if/else. Класс
становится огромным и сложным. Добавление нового статуса заставит нас открыть
этот класс и добавлять новые условия во все методы, что нарушает принцип
открытости/закрытости

Проблема 2 — Нарушение принципа единой ответственности:
Класс Order отвечает одновременно за хранение данных заказа, логику перехода
между статусами и реализацию поведения для каждого из этих статусов

Проблема 3 — Трудночитаемый и непредсказуемый код:
Условия могут быть сложными и дублироваться в разных методах. Это повышает риск
ошибок и усложняет понимание логики работы приложения

3) Структура паттерна Состояние:

                ┌──────────────────────────────────────────┐
                │                 Context                  │
                │                (Контекст)                │
                ├──────────────────────────────────────────┤
                │ - state: State*                          │
                ├──────────────────────────────────────────┤
                │ + request(): void {                      │
                │     state->handle(this);                 │
                │ }                                        │
                │ + setState(State*): void                 │
                └─────────────────────┬────────────────────┘
                                      |
                                      │ содержит
                                      ▼
                ┌──────────────────────────────────────────┐
                │                  State                   │
                │           (Интерфейс состояния)          │
                ├──────────────────────────────────────────┤
                │ + handle(Context*): void                 │
                └──────────────────────────────────────────┘
                                      ▲
                       ┌──────────────┴──────────────┐
                       │                             │
           ┌───────────┴────────────┐   ┌────────────┴───────────┐
           │     ConcreteStateA     │   │     ConcreteStateB     │
           | (Конкретное состояние) |   | (Конкретное состояние) |
           ├────────────────────────┤   ├────────────────────────┤
           │ + handle(Context* c)   │   │ + handle(Context* c)   │
           └────────────────────────┘   └────────────────────────┘

Ключевые компоненты:
• Context (Контекст): Класс, который хранит ссылку на текущее состояние и
делегирует ему выполнение работы. Это основной объект, поведение которого мы
хотим изменять. Контекст предоставляет метод setState() для смены состояния
• State (Состояние): Интерфейс, который определяет общее поведение для всех
конкретных состояний. Обычно он содержит один или несколько методов, которые
контекст будет вызывать
• ConcreteState (Конкретные состояния): Классы, реализующие интерфейс State.
Каждый такой класс содержит код, специфичный для определенного состояния
контекста. В этих методах также может происходить логика переключения
контекста на другое состояние

4) Ключевые преимущества паттерна:
• Избавляет от огромных условных операторов — Весь код, связанный с конкретным
состоянием, инкапсулируется в соответствующем классе. Это делает код контекста
чистым и понятным
• Принцип единой ответственности — Каждый класс состояния отвечает только за
поведение в рамках одного конкретного состояния
• Принцип открытости/закрытости — Новые состояния можно легко добавлять,
создавая новые классы и не изменяя существующие классы состояний или контекст
• Локализация кода — Код, относящийся к одному состоянию, не разбросан по
всему классу, а собран в одном месте
• Упрощение контекста — Контекст становится проще, так как его основная
задача — хранить данные и делегировать выполнение методов текущему состоянию
• Явные переходы между состояниями — Переключения между состояниями становятся
более явными и контролируемыми, так как они выполняются внутри методов
конкретных состояний

5) Когда применять паттерн?
✓ Когда поведение объекта зависит от его состояния и может изменяться во время
выполнения
✓ Когда в коде объекта используются огромные условные операторы, которые
выбирают поведение в зависимости от текущего состояния
✓ Когда код сильно "замазан" условиями, и добавление нового состояния требует
изменения многих методов существующего класса
✓ Когда состояния могут содержать повторяющиеся участки кода, которые можно
вынести в общий базовый класс или интерфейс
✓ Когда объект должен иметь разное поведение в разных состояниях, и это
поведение логически независимо

6) Важные замечания!
⨯ Усложнение структуры — Паттерн требует создания множества дополнительных
классов. Если состояний всего 2-3 и они редко меняются, введение паттерна
может быть избыточным
⨯ Неожиданные переходы — Неправильная реализация смены состояний внутри методов
ConcreteState может привести к неочевидным и трудноотлаживаемым переходам,
если логика становится слишком сложной
⨯ Дублирование кода между состояниями — Если несколько состояний имеют похожее
поведение, может возникнуть соблазн скопировать код. В этом случае следует
подумать о создании абстрактного базового класса для состояний или
использовании паттерна "Стратегия" для композиции внутри состояний


                       Паттерн "Стратегия" (Strategy)
1) Суть паттерна парой слов:
Стратегия — это поведенческий паттерн проектирования, который определяет
семейство схожих алгоритмов и помещает каждый из них в собственный класс.
Паттерн позволяет подменять используемый алгоритм прямо во время выполнения
программы, делая поведение объекта независимым от его клиентов. Вместо жесткой
реализации конкретного поведения внутри класса, объект делегирует выполнение
одной из взаимозаменяемых стратегий

2) Проблема, которую решает паттерн:
Представьте, что мы пишем модуль навигатора, который строит маршруты. Сначала
он умел строить только автомобильные маршруты. Код прокладки маршрута был прямо
прописан в классе Navigator. Но клиент просит добавить маршруты для пешеходов и
велосипедистов

Проблема 1 — Разрастание условных конструкций:
Самый очевидный, но плохой путь — добавлять в метод построения маршрута
операторы if/else, чтобы выбрать нужный код в зависимости от типа маршрута

Проблема 2 — Нарушение принципа открытости/закрытости:
При добавлении нового алгоритма (например, "общественный транспорт") нам
придется открывать и изменять уже оттестированный и работающий класс Navigator.
Это увеличивает риск внесения ошибок в существующий код

Проблема 3 — Дублирование кода и сложность поддержки:
Если два разных типа маршрутов используют общие участки логики, код будет
дублироваться в разных ветках if/else. Также класс Navigator будет перегружен
обязанностями

3) Структура паттерна Стратегия:

                       ┌───────────────────────────────────┐
                       │              Context              │
                       │             (Контекст)            │
                       ├───────────────────────────────────┤
                       │ - strategy: Strategy*             │
                       ├───────────────────────────────────┤
                       │ + setStrategy(Strategy*)          │
                       │ + executeBehavior(): void         │
                       └─────────────────┬─────────────────┘
                                         │
                                         │  использует
                                         ▼
                       ┌───────────────────────────────────┐
                       │             Strategy              │
                       │       (Интерфейс стратегии)       │
                       ├───────────────────────────────────┤
                       │ + algorithm(): void               │
                       └───────────────────────────────────┘
                                         ▲
                  ┌──────────────────────┼──────────────────────┐
        ┌─────────┴─────────┐  ┌─────────┴─────────┐  ┌─────────┴─────────┐
        │ ConcreteStrategyA │  │ ConcreteStrategyB │  │ ConcreteStrategyC │
        ├───────────────────┤  ├───────────────────┤  ├───────────────────┤
        │ + algorithm()     │  │ + algorithm()     │  │ + algorithm()     │
        └───────────────────┘  └───────────────────┘  └───────────────────┘

Ключевые компоненты:
• Context (Контекст): Класс, который хранит ссылку на объект-стратегию.
Контекст не знает конкретного типа стратегии — он работает с ней через общий
интерфейс Strategy. Именно контекст решает, какую стратегию выбрать и когда её
применить
• Strategy (Стратегия): Общий интерфейс, общий для всех конкретных стратегий.
Обычно содержит единственный метод. Контекст будет использовать этот интерфейс
для вызова алгоритма
• ConcreteStrategy (Конкретная стратегия): Класс, реализующий конкретный
вариант алгоритма. Все конкретные стратегии взаимозаменяемы, так как реализуют
один и тот же интерфейс

4) Ключевые преимущества паттерна:
• Принцип открытости/закрытости — Можно вводить новые алгоритмы (стратегии),
не изменяя существующие классы контекста и клиентов
• Изоляция кода и данных — Алгоритмы выносятся в отдельные классы. Можно
работать над оптимизацией одного алгоритма, не боясь сломать другой
• Замена наследования делегированием — Вместо наследования используется
композиция, что делает код более масштабируемым
• Устранение условных конструкций — Код перестает быть "спагетти" из if/else.
Выбор стратегии сводится к одной строке — вызову метода интерфейса у
подставленного объекта
• Гибкость во время выполнения — Поведение объекта можно изменить "на лету",
просто подменив один объект стратегии другим

5) Когда применять паттерн?
✓ Когда есть несколько родственных классов, которые отличаются только
поведением. Например, разные способы валидации данных, сжатия файлов,
расчета налогов
✓ Когда нужно иметь несколько вариантов одного алгоритма, и выбор между ними
происходит по условию
✓ Когда алгоритмы используют данные, которые клиент не должен знать. Стратегия
может инкапсулировать сложные структуры данных, не раскрывая их контексту
✓ Когда алгоритм зависит от состояния системы или внешних факторов, которые
могут меняться во время выполнения программы
✓ Когда система не должна "завязываться" на конкретных реализациях алгоритмов.
Это позволяет легко заменять одну реализацию на другую

6) Важные замечания!
⨯ Усложнение кода — Паттерн требует введения дополнительных классов и
интерфейсов. Если алгоритмов всего 1-2 и они меняются крайне редко, вводить
паттерн будет избыточно
⨯ Клиент должен знать о стратегиях — Часто именно клиентский код должен решить,
какую конкретную стратегию подложить в контекст. Это означает, что клиент
должен быть осведомлен о существовании различных стратегий и их отличиях, что
может увеличить сложность клиентского кода
⨯ Передача данных — Сложность возникает, когда разные стратегии требуют
разного набора входных параметров. Не всегда можно уместить все необходимые
данные в универсальный метод интерфейса Strategy


                 Паттерн "Шаблонный метод" (Template Method)
1) Суть паттерна парой слов:
Шаблонный метод — это поведенческий паттерн проектирования, который определяет
«скелет» алгоритма в методе суперкласса, позволяя подклассам переопределять
определенные шаги алгоритма, не меняя его общей структуры. Паттерн предлагает
разбить алгоритм на последовательность шагов, оформить эти шаги как методы, а
вызовы этих методов поместить в один «шаблонный» метод. Подклассы могут
переопределять некоторые из шагов, но не могут изменить сам шаблонный метод

2) Проблема, которую решает паттерн:
Представьте, что мы разрабатываем систему для сборки отчетов. У нас есть отчет
в формате PDF и отчет в формате HTML. Процесс создания обоих отчетов одинаков:
открыть файл, записать заголовок, записать содержимое, закрыть файл

Проблема 1 — Дублирование кода:
Если мы создадим два независимых класса PdfReport и HtmlReport, то код для
открытия и закрытия файла будет одинаковым и продублируется в обоих классах

Проблема 2 — Нарушение принципа "Не повторяй себя" (DRY):
Изменение логики открытия файла потребует правки в обоих классах, что повышает
риск ошибок

Проблема 3 — Размытие структуры алгоритма:
При чтении кода каждого из классов не сразу видна общая последовательность
действий. Алгоритм «размазан» по методам, и его логику приходится
восстанавливать

3) Структура паттерна Шаблонный метод:

                ┌─────────────────────────────────────────────┐
                │           AbstractClass (Шаблон)            │
                │             (Абстрактный класс)             │
                ├─────────────────────────────────────────────┤
                │ + templateMethod(): void {                  │
                │     stepOne();                              │
                │     stepTwo();                              │
                │     stepThree();                            │
                │     if (hook()) { optionalStep(); }         │
                │ }                                           │
                ├─────────────────────────────────────────────┤
                │ # stepOne(): void        // абстрактный     │
                │ # stepTwo(): void        // абстрактный     │
                │ # stepThree(): void      // конкретный      │
                │ # optionalStep(): void   // конкретный      │
                │ # hook(): bool           // перехватчик     │
                └─────────────────────────────────────────────┘
                                       ▲
                                       │
                    ┌──────────────────┴──────────────────┐
                    │                                     │
        ┌───────────┴────────────┐           ┌────────────┴───────────┐
        │     ConcreteClassA     │           │     ConcreteClassB     │
        │   (Конкретный класс)   │           │   (Конкретный класс)   │
        ├────────────────────────┤           ├────────────────────────┤
        │ # stepOne(): void {    │           │ # stepOne(): void {    │
        │     // своя реализация │           │     // своя реализация │
        │ }                      │           │ }                      │
        ├────────────────────────┤           ├────────────────────────┤
        │ # stepTwo(): void {    │           │ # stepTwo(): void {    │
        │     // своя реализация │           │     // своя реализация │
        │ }                      │           │ }                      │
        ├────────────────────────┤           ├────────────────────────┤
        │ # hook(): bool {       │           │ # hook(): bool {       │
        │     return true;       │           │     return false;      │
        │ }                      │           │ }                      │
        └────────────────────────┘           └────────────────────────┘

Ключевые компоненты:
• AbstractClass (Шаблон): Aбстрактный класс, который содержит шаблонный метод
templateMethod(), определяющий неизменяемый скелет алгоритма и вызывающий шаги
в заданном порядке; а так же содержит шаги алгоритма, которые могут быть
абстрактными или конкретными по умолчанию
• ConcreteClass (Конкретный класс): Реализует абстрактные методы-шаги,
определенные в AbstractClass, может переопределять методы-перехватчики (hook),
если это необходимо для его логики

4) Ключевые преимущества паттерна:
• Инкапсуляция инвариантов — Общая часть алгоритма (неизменяемая) выносится в
базовый класс, что упрощает ее поддержку
• Устранение дублирования кода — Общие шаги реализуются один раз в базовом
классе, а не дублируются в каждом подклассе
• Принцип "Не повторяй себя" (DRY) — Логика, общая для всех вариаций алгоритма,
централизована
• Принцип голливуда (Hollywood Principle) — "Не звоните нам, мы сами вам
позвоним". Родительский класс управляет ходом выполнения и вызывает методы
подклассов, а не наоборот. Это уменьшает зависимость подклассов от деталей
реализации родительского класса
• Гибкость через переопределение — Подклассы могут уточнять поведение отдельных
шагов, не меняя структуру алгоритма

5) Когда применять паттерн?
✓ Когда несколько классов имеют похожие алгоритмы, отличающиеся лишь деталями
отдельных шагов
✓ Когда нужно избежать дублирования кода, вынося общую логику в базовый класс
✓ Когда структура алгоритма должна быть централизованно управляемой, а его
детали могут варьироваться в подклассах
✓ Когда требуется контролировать точки расширения подклассов, разрешая им
переопределять только определенные операции, но не структуру алгоритма

6) Важные замечания!
⨯ Ограничение гибкости — Шаблонный метод жестко фиксирует структуру алгоритма.
Изменить порядок шагов в подклассе невозможно. Если алгоритм должен быть более
гибким, лучше рассмотреть паттерн Стратегия
⨯ Сложность понимания иерархии — Для понимания конечного поведения конкретного
класса нужно держать в голове как код самого класса, так и код его абстрактного
предка
⨯ Может привести к разрастанию иерархии — Для каждой новой вариации алгоритма
может потребоваться создавать новый подкласс. Если вариаций много, это может
стать проблемой, которую паттерн Стратегия решает более элегантно через
композицию


                       Паттерн "Посетитель" (Visitor)
1) Суть паттерна парой слов:
Посетитель — это поведенческий паттерн проектирования, который позволяет
добавлять новые операции для целой иерархии классов, не изменяя эти классы.
Паттерн выносит алгоритмы, выполняемые над объектами, в отдельные классы
«посетители». Когда такой «посетитель» проходит по структуре объектов (например,
по дереву), каждый объект вызывает соответствующий метод посетителя, передавая
себя в качестве параметра. Это позволяет объекту и операции над ним развиваться
независимо друг от друга

2) Проблема, которую решает паттерн:
Представьте, что наша программа моделирует зоопарк. У нас есть иерархия классов
животных: Lion (Лев), Monkey (Обезьяна), Elephant (Слон). Мы хотим добавить
функциональность, например, операцию «покормить» и «осмотреть у ветеринара»

Проблема 1 — Засорение классов новым функционалом:
Самый простой способ — добавить новые методы (feed(), healthCheck()) прямо в
каждый класс животного. Но что, если нам понадобится множество таких операций:
«подсчитать еду на месяц», «выдать звук», «перевезти в другой вольер»? Классы
животных будут постоянно расти и меняться по причинам, не связанным с их
прямой обязанностью

Проблема 2 — Нарушение принципа открытости/закрытости:
Каждый раз, когда требуется добавить новую операцию, придется модифицировать и
компилировать заново все классы животных. Это нарушает принцип
открытости/закрытости

Проблема 3 — Группировка родственных операций:
Код для родственных операций разбросан по разным классам животных. Если
изменится логика кормления, нам придется искать и править эту логику в классе
каждого животного. Это неудобно и чревато ошибками

3) Структура паттерна Посетитель:

            ┌──────────────────────────────────────────────────────┐
            │                        Client                        │
            └──────────────────────────┬───────────────────────────┘
                                       │
                                       │ использует
                ┌──────────────────────┴─────────────────────┐
                │                                            │
                ▼                                            ▼
  ┌───────────────────────────┐                ┌────────────────────────────┐
  │          Element          │                │          Visitor           │
  │         (Элемент)         │                │        (Посетитель)        │
  ├───────────────────────────┤                ├────────────────────────────┤
  │ + accept(v: Visitor*)     │◄──────────────►│ + visitLion(Lion*)         │
  └───────────────────────────┘                │ + visitMonkey(Monkey*)     │
                ▲                              │ + visitElephant(Elephant*) │
                │                              └────────────────────────────┘
                └──────┐                                      ▲
            ┌──────────┴──────────┐                           │ реализует
            │                     │                           │
  ┌─────────┴────────┐   ┌────────┴─────────┐   ┌─────────────┴──────────────┐
  │       Lion       │   │      Monkey      │   │      ConcreteVisitor       │
  ├──────────────────┤   ├──────────────────┤   │      (FeedingVisitor)      │
  │ + accept(v) {    │   │ + accept(v) {    │   ├────────────────────────────┤
  │   v->visitLion   │   │   v->visitMonkey │   │ + visitLion(Lion*)         │
  │   (this);        │   │   (this);        │   │ + visitMonkey(Monkey*)     │
  │ }                │   │ }                │   │ + visitElephant(Elephant*) │
  └──────────────────┘   └──────────────────┘   └────────────────────────────┘

Ключевые компоненты:
• Visitor (Посетитель): Интерфейс, который объявляет методы посещения для
каждого конкретного типа элементов. Имена методов явно указывают, с каким
классом элемента они работают
• ConcreteVisitor (Конкретный посетитель): Реализует все методы, объявленные в
интерфейсе Visitor. Каждый конкретный посетитель отвечает за одну операцию,
выполняемую над всей структурой объектов (например, FeedingVisitor реализует
логику кормления для каждого типа животного)
• Element (Элемент): Интерфейс, который объявляет метод accept(). Этот метод
принимает объект посетителя в качестве аргумента
• ConcreteElement (Конкретный элемент): Классы (Lion, Monkey, Elephant),
которые реализуют метод accept(). Реализация всегда одинакова и очень проста:
visitor->visit(this). Вызов направляется обратно к посетителю, но с передачей
конкретного типа элемента

4) Ключевые преимущества паттерна:
• Принцип открытости/закрытости — Можно добавлять новые операции (посетителей),
не изменяя код уже существующих классов элементов. Достаточно создать нового
посетителя
• Принцип единой ответственности — Код, относящийся к одной операции,
собирается в одном классе-посетителе. Классы элементов занимаются только своим
прямым делом
• Группировка родственных операций — Все варианты одной операции находятся в
одном месте, что упрощает их поддержку и модификацию
• Накопление состояния — Посетитель может накапливать состояние по мере обхода
структуры
• Двойная диспетчеризация (Double Dispatch) — Паттерн реализует механизм
двойной диспетчеризации. Выполняемый код зависит и от типа элемента, и от типа
посетителя

5) Когда применять паттерн?
✓ Когда нужно выполнить какие-то операции над всеми элементами сложной
структуры объектов и эти операции не связаны с самими объектами
✓ Когда в иерархию классов нужно добавить новое поведение, но изменение или
компиляция существующих классов по каким-то причинам затруднены
✓ Когда классы в иерархии редко меняются, но новые операции над ними
добавляются часто
✓ Когда поведение должно быть одинаковым для объектов разных классов, но его
реализация зависит от конкретного класса объекта
✓ Когда алгоритмы, выполняемые над объектами, имеют смысл хранить отдельно от
самих объектов

6) Важные замечания!
⨯ Нарушение инкапсуляции — Паттерн требует, чтобы посетитель имел доступ к
внутреннему состоянию элементов для выполнения операций. Это может привести к
тому, что элементы будут вынуждены раскрывать свои приватные данные или
предоставлять для этого публичные методы
⨯ Сложность добавления новых элементов — Если иерархия элементов часто
расширяется, то это плохой выбор
⨯ Циклические зависимости — Интерфейсы Element и Visitor должны знать друг о
друге, что может создать циклическую зависимость в коде
⨯ Избыточность для простых структур — Для простого списка однотипных объектов
или для иерархии, которая редко нуждается в новых операциях, паттерн может
быть излишне сложным
